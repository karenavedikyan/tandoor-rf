# Самостоятельная регистрация внешнего пользователя в MAX и Telegram

Разрешение владельца: «Да, разрешаю самостоятельную регистрацию в MAX и Telegram». Реализация локальная, без push/PR/merge/deploy.

## Сценарий

- Новый пользователь выбирает «Создать передачу» и отправляет собственный контакт штатной кнопкой.
- Подтверждённый личный контакт создаёт внешний профиль и канонический глобальный внешний контакт по номеру, даже если номер ранее не был в Тандор.
- В ответе есть штатное меню с «Создать передачу»; затем пользователь проходит обычный сценарий первой передачи.
- Для MAX добавлено меню после подтверждения и проверка личного диалога перед общей регистрацией. Telegram отбрасывает групповые контактные события в существующем парсере.
- Уже существующий контакт/профиль переиспользуется. Повтор webhook не создаёт новую сессию или профиль.

## Каноническая реализация

- `upsertVerifiedPerson` получил серверный opt-in `allowSelfRegistration`; по умолчанию неизвестный номер по-прежнему запрещён.
- Только общая бот-обёртка, вызываемая после проверки собственного контакта, включает этот opt-in. Публичных параметров для его включения нет.
- Новая party создаётся через `resolveOrCreateGlobalExternalPartyByPhone`, без нового реестра, миграции или роли сотрудника.
- Транзакционные блокировки messenger identity → phone сериализуют регистрацию. MAX и Telegram с одним номером получают один профиль и одну party; один messenger ID нельзя одновременно перепривязать к двум разным телефонам.
- Текстовые цифры, чужой контакт, пересылка, неверная подпись MAX и группа не регистрируют пользователя.
- Коллизии с номером сотрудника, неоднозначные контакты и уже связанный с другим номером messenger отклоняются. Ожидаемый отказ объясняется в чате; SQL/неожиданные ошибки откатываются.
- Scope списков/карточек, OTP, фактический приём, уведомления и право завершения не расширены. Новому профилю доступны только его собственные передачи.
- Нормализация номеров не менялась; новые международные коды не добавлялись.

## Проверки

- Новый сквозной webhook-сценарий в каждом канале: неизвестный номер → отказы чужому/пересланному/групповому контакту и неверной подписи MAX без записей → собственный контакт → профиль/сессия → первая передача → отсутствие доступа к чужой карточке.
- Два новых конкурентных PG-теста: общий номер в MAX/Telegram не дублируется; один messenger ID с двумя номерами связывается только один раз.
- 249 целевых интеграционных проверок прошли: 243 в `/tmp/tandoor-self-registration-integration.log` вне устаревшего unified-recipient набора, ещё 6 messenger invite authority/Telegram receipt в `/tmp/tandoor-self-registration-followup.log`.
- Дополнительный старый `tandoor-independent-unified-recipient.test.ts` не объявляется зелёным: его 24 сценария изначально останавливаются на устаревшем ожидании «Пропустить» вместо существующей до этой задачи кнопки «Без вложений». Временная адаптация первого шага оставила 12 отказов на старых сценариях поиска по имени. Изменения этого не относящегося к задаче набора отменены, файл не включён в правку.
- Unit итогового блока с предпросмотром приглашения: 1436/1436, `/tmp/tandoor-self-registration-and-preview-unit.log`. До UI-правки unit регистрационного блока: 1435/1435.
- Typecheck/build/JS syntax/diff-check: PASS. `/tmp/tandoor-self-registration-and-preview-{typecheck,build}.log`.

Production-номер со скриншотов, живые бот-события и отправка из реальных приложений не проверялись. Все записи и сетевые имитации в проверках относятся только к отдельным синтетическим тестовым БД; production, env, webhook, DNS, роли и worker не изменялись.
