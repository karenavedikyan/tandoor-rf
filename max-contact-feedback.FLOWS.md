# MAX: контакт без молчания и подтверждение найденного получателя

- База: текущий production `4b7a3a8d9e4e64a60c7579bedc4d6a5e3a1f1fe0`. Отдельная ветка; без PR/merge/deploy, реальных сообщений и production-данных.
- По скриншоту нельзя установить содержимое исходного webhook. Подтверждён кодовый сценарий: contact без непустого `vcf_info` не распознаётся как контакт; при `body.text=""` parser возвращает `empty_text`, handler молчит.
- MAX response `ContactAttachmentPayload.vcf_info` optional/nullable: https://dev.max.ru/docs-api/objects/Message. Наличие имени/аватара/MAX ID не гарантирует номер.
- Распознавать карточку без VCF как неподтверждённые данные получателя, включая пустой/отсутствующий/null/malformed payload. Пустая строка VCF означает отсутствие данных, не синтетический номер.
- В активном recipient-шаге явно ответить «В карточке контакта нет номера телефона. Введите номер вручную или отправьте контакт с номером». Не менять черновик и не выбирать получателя по имени/ID.
- При наличии номера сохранить существующий поиск и проверку доступности. Одна найденная запись: «Получатель найден. Нажмите кнопку с его именем, чтобы подтвердить выбор». Несколько: «Выберите получателя из списка». Повторный ввод телефона не предлагать после успешного поиска.
- Signed request_contact/HMAC, проверка собственной личности, приватность, forwarded/group guards и дедупликация не изменяются. Неподтверждённая карточка не подтверждает личность и не создаёт трек/OTP/уведомления.
- Вне подходящего мастера не выдавать ложного принятия контакта; действующий безопасный fallback меню сохраняется.
- Проверки: parser для типовых карточек без/с VCF, отсутствие молчания при пустом text, signed contact не превращается в unsigned, приватный чат/forward guards, оба канала для текста выбора, реальные webhook pipeline на локальной *_test БД с перехваченным транспортом. Не возвращаться к незапрошенной реализации нижнего меню Telegram.

## Дополнение владельца: повторный запрос

- Переименовать «Получить код у получателя» в «Запросить код повторно» в обоих каналах и связанных подсказках.
- Так же назвать уже существующую кнопку retry в режиме ввода. Callback/action, выдача OTP, получатели и способы доставки остаются прежними.

## Результат проверки

- `npm run typecheck`, `npm run build`, `git diff --check`: PASS.
- `npm test`: 1395/1395 PASS, отдельная локальная unit-БД.
- Четыре integration-файла, всего 105 разных сценариев: первый набор 51 PASS и четыре исправленных тестовых ожидания после выбора получателя; второй набор 49 PASS и одно устаревшее ожидание текста compact menu. Четыре сценария phone/contact затем отдельно PASS, последний fallback отдельно PASS. Код приложения после общих прогонов не менялся; единый зелёный прогон 105/105 не заявляется.
- Набор: independent-recipient-contact (22), native-receipt-entry (33), independent-bot-main-menu и independent-native-recipient-contact (вместе 50). Без реальной сети, только локальная `*_test` БД и записывающие транспорты.
- Подтверждены ответы на карточку без VCF и пустой text, отсутствие изменения черновика/идентичности/треков/OTP, дедупликация, group/forward guards, сохранение signed own-contact маршрута, обработка номера из карточки и текста с подтверждением выбора в обоих каналах.
- Старые test fixtures приведены к уже опубликованным «Без вложений» и compact menu; бизнес-проверки и запрет ложного принятия контакта сохранены.
- Миграций, production-операций, изменений env/webhook/ролей/workers нет. Нижнее меню Telegram не изменялось: на предложение варианта разрешения ещё не получено.
- Ограничение диагноза: исходного webhook показанного контакта нет, raw payload не сохраняется в inbox. Проверен и устранён конкретный кодовый сценарий, но нельзя доказать, что именно он сработал у пользователя.
