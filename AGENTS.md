# Tandoor RF: правила выполнения задач

## Экономное выполнение без потери качества

Правило владельца проекта от 30.09.2026: перед каждой задачей выбирать самый простой достаточный способ выполнения, избегать лишнего расхода кредитов и не замедлять продвижение проекта.

1. **Сначала переиспользование.** Проверить имеющийся код, документы, результаты проверок и готовые функции. Не повторять полный аудит проекта ради локальной правки.
2. **Обычный код вместо ИИ, где возможно.** Фильтрацию, сравнение файлов, расчёты, проверки типов, сборку и повторяемые проверки выполнять скриптами и штатными инструментами. Не поручать модели работу, которую надёжно выполняет существующий инструмент.
3. **Один исполнитель изменений.** Небольшие правки делать напрямую. Для крупного блока выбрать одного исполнителя, например Cursor; второй участник проверяет результат, а не пишет ту же реализацию заново. Не запускать дополнительные модели или параллельных агентов без конкретной необходимости и разрешения в текущей задаче.
4. **Точный объём до начала.** Зафиксировать результат, границы, критерии приёмки и затрагиваемые файлы. Все замечания одного просмотра передавать одним сообщением, не дробить на цепочку почти одинаковых промптов.
5. **Проверки по риску.** Использовать результаты для конкретного SHA, не переносить их автоматически на изменённый код. После локальной правки запускать затронутые тесты и необходимые общие проверки; полный регрессионный прогон нужен при изменениях общих контрактов, прав, идентичностей, миграций или широком влиянии. Не повторять успешно завершённый неизменный тест без причины.
6. **Прямые инструменты прежде браузера.** Использовать API/CLI для репозитория, статусов и развёртывания. Браузер нужен для визуальной проверки, пользовательского сценария или функции, недоступной другим способом. Не снимать одинаковые скриншоты повторно.
7. **Выпуск законченного блока.** Один PR и один деплой на согласованный рабочий результат, не на каждую мелкую правку. Документальное изменение без влияния на приложение не требует деплоя.
8. **Ожидание без бесконечных циклов.** Проверять деплой с разумными интервалами, не повторять сборку без признаков сбоя. При зависании: одна диагностика, при наличии разрешения один обоснованный повторный запуск; при повторной неудаче зафиксировать блокер вместо бесконечных попыток.
9. **Короткая коммуникация.** Сообщать результат, блокер и ближайшее действие. Длинный отчёт, презентацию или дополнительный прототип создавать только по необходимости или запросу.
10. **Без обещаний стоимости.** API, тесты и браузер не объявлять «бесплатными». Без фактических данных не оценивать кредиты, не обещать процент экономии и не считать перенос работы в Cursor автоматически более дешёвым.

## Что нельзя сокращать ради экономии

- Проверки серверных прав, изоляции клиентов, запрета раскрытия закрытых задач и корректности идентификаторов.
- Проверки сохранности данных, миграций и возможности отката при соответствующих изменениях.
- Проверку основного затронутого сценария после развёртывания.
- Соответствие согласованному прототипу, логотипу, фирменным цветам и существующей дизайн-системе.

Импорт 1С и задания по расписанию не запускать до отдельного разрешения владельца. Не расширять пилот, не выдавать новые права и не изменять данные во внешних системах только на основании права на merge/deploy.

Разрешения определяются текущей задачей и решениями владельца. Устаревшие статусы PR в исторических документах не подменяют актуальное состояние GitHub.

## Для промптов Cursor

Каждый новый промпт должен учитывать этот файл и содержать: один результат, границы изменений, нужные проверки, запреты и краткий формат сдачи (SHA, тесты, ограничения). Не запрашивать повторное исследование уже подтверждённых фактов.

## Единая очередь R2

Решение владельца от 01.10.2026: документы и возвраты являются обычными задачами/чек-листами Битрикс24 в общей очереди ЛК, а не отдельными процессами. Не создавать дубли задач или независимые статусы; отдельный фильтр документов возможен только при подтверждённой пользе.

Рекламации также остаются задачами Битрикс24; менеджеру без полного доступа показывать только опубликованную специалистом разрешённую сводку. Перед разработкой проверить существующий механизм и реализовать только недостающее, не расширяя права. Полный R2 не объявлять закрытым до приёмки этого сценария. Подробности: [план релизов, R2](docs/delivery/release-plan.md#r2--моя-работа-и-общий-контекст).
