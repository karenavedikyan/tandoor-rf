## R1 — «Мои клиенты» (первый полезный продуктовый релиз)

### Сценарий (v1.1)

Сотрудник входит → видит **свою базу** → находит клиента → открывает контакт/адрес/условия → видит ответственного и **дату обновления**.

| R1.3 | Идентичности и серверные права (user ↔ ID сотрудника 1С) | матрица ролей и прав |
| **R1.3-prep** | **Матрица ролей, правил и сценариев приёмки (docs only)** | main; **не** заменяет R1.3 |
| R1.4 | Рабочая карточка по прототипу (список, поиск, обзор, паспорт, доступ, источники) | R1.1–R1.3 |

**Экраны прототипа v2 (целевые):** clients, overview, passport, access, sources; team — только список разрешённой команды/клиентов без оценок эффективности.

**Приёмка R1:** два менеджера не видят чужие записи (в т.ч. через прямой API); РОП видит свою команду; обновление не дублирует клиентов; реквизиты у верного юрлица; телефоны и адреса пригодны для работы.

### R1.4-prep — ограниченный объём (согласовано владельцем)

**Разрешено:** список и карточка «Клиенты» на **8 подтверждённых полях** + `last_imported_at`; поиск/фильтры/пагинация; возврат с сохранением состояния; блоки «Данные 1С», «Источник и обновление»; компактные заглушки будущих данных; admin-only.

**Запрещено этим этапом:** снятие `requireAdmin`; коммерческие поля; импорт/БД/FTP; пилот сотрудников; заявление «100% прототип v2»; завершение R0.2 / R1.1–R1.3 / R1.4.

### R1.3-prep — матрица ролей и прав (docs only)

**Разрешено:** документы [access-matrix.md](./access-matrix.md), [access-rules.md](./access-rules.md), [access-acceptance-scenarios.md](./access-acceptance-scenarios.md); ссылки в README и acceptance-matrix.

**Запрещено:** изменение кода, БД, миграций, enum ролей, `requireAdmin`, импорта; выдача реальных доступов; заявление «R1.3 реализован»; разрешение пилота; изменение UI/бренда (PR #12).

**Целевая модель (предложение, на согласование):** роли `assistant` + `coordinator` и таблица `delegations` — потребуют migration при реализации R1.3/R4.3.

**Не закрывает:** R0.2, R1.1, R1.2, R1.3 (implementation), R1.4, R1.5.

**Блокеры финальной приёмки R1.4:** Golos vs Exo 2 (владелец); сверка с PDF прототипом v2; R1.1–R1.3; семантика `guid_client` (1С).

### На существующем обмене (8 полей JSON)

`guid_client`, `name_client`, `guid_holding`, `name_holding`, `guid_manager`, `name_manager`, `address`, `telephone` + `last_imported_at` в БД.

### По готовности новой выгрузки 1С

Холдинг как сущность, юрлица, ТТ, реквизиты, договоры, региональный, РОП, коммерческие условия. **Отсутствующие сведения не имитируем.**

### Ограниченный пилот без идеальной базы

Допустим на существующих записях и **подтверждённых назначениях**, если расширение 1С задержится. Нельзя: объявлять плоскую запись юрлицом/ТТ; давать региональному доступ без проверенного назначения.

**Предлагаемый состав пилота (v1.1):** один РОП + 2–3 менеджера; региональный при готовых назначениях. Это предложение, не выбранные участники.

### Без чего нельзя выпускать даже ограниченный пилот

1. Модель связи `users` ↔ ID сотрудника 1С (не сопоставление только по ФИО).
2. Серверная фильтрация по роли (**не** снятие `requireAdmin`).
3. Runbook импорта (расписание, `onec_client_import_runs`, обработка ошибок).
4. Решение по фирменному эталону — [brand-contract.md](./brand-contract.md).

### За пределами R1

Заказы, финансовый контроль, полноценное замещение, витрины, KPI, прогноз, каталог как самостоятельный раздел, CRM-функции.

### Принципы данных

- Холдинг = клиент в модели v1.1; юрлица и ТТ — отдельно; связи **явно** из источника.
- Адрес доставки ≠ ТТ автоматически.
- ЛК — единое окно, **не** новая CRM и не второй справочник клиентов.

### Замечание аудита 28.09 (v1.1, требует повторной проверки источника)

В файле клиентов на FTP — 3 824 записи, в БД — 3 808; скидки и наценки не сохраняются. Товарный блок на FTP есть, в новом ЛК не подключён. Расширенный обмен готовит 1С-специалист.

## FTP: код vs разрешённая область (v1.1)

**Код (main):** `ONEC_FTP_BASE_PATH` обязателен, default нет; `CLIENTS_RELATIVE_PATH = "clients/all_clients.json"`; итог = `{basePath}/clients/all_clients.json` (`buildClientsFilePath`). Пример: base `/LC` → `/LC/clients/all_clients.json`.

**Политика v1.1** (не путать с env):

| Путь (при base `/LC`) | Назначение | ЛК |
|-----------------------|------------|-----|
| `/LC/clients/all_clients.json` | Snapshot клиентов | импорт CLI |
| `/LC/catalog/` | Товарный блок | не подключён |
| Заказы/финансы | O01–O07 | не согласованы |
