# Постоянные миниатюры каталога

## Граница

Только производные фото раздела `/internal-catalog`. Товары, исходные GUID,
группировка размеров, цены/остатки, история и оригинальные фото не изменяются.
Не запускаются импорт 1С, расписания, сообщения или новые фоновые процессы.
Настройки окружения, S3, DNS, webhook и роли не меняются.

В production-проверке 14.11.2026 приложение использовало backend `local`,
`INTERNAL_CATALOG_IMAGE_BACKEND=shared`, без подключённых S3-ключей.
Наличие бакета в аккаунте не означает, что приложение умеет его читать.
Поэтому для небольших производных используется существующий постоянный PostgreSQL,
а не временный диск контейнера. Изображения не делаются публичными.

## Контракт

- Добавочная миграция `085_internal_catalog_thumbnails.sql`, одна новая таблица.
- Ключ: исходный snapshot UUID + нормализованный source path + версия рецепта.
- Один источник, использованный разными SKU, готовится один раз. SKU не объединяются.
- Подготовка не загружает `record` товаров и полный список путей в Node.js.
  PostgreSQL извлекает и дедуплицирует нормализованные `files.path`; приложение
  читает только пути порциями до 64 строк, с keyset-переходом и сортировкой `C`.
  Общее число путей и занятые байты получаются агрегатным запросом.
  Проверка готовых миниатюр, пропуск прежних ошибок без `--retry-failed` и
  лимит попыток действуют между порциями. Схема БД и исходные записи не меняются.
  БД по-прежнему читает JSON для извлечения путей: это ограничение передачи
  и накопления данных в приложении, не обещание отсутствия сканирования в БД.
  Изменение не является жёстким ограничителем памяти декодера изображений;
  новую production-пробу с контролем памяти нужно согласовать отдельно.
- WebP без EXIF, без обрезки/увеличения: `small` до 240px/32KiB,
  `list` до 640px/128KiB, качество 76.
- «Таблица» и лента фото карточки используют `small`; оба карточных режима списка
  используют `list`. Основное фото карточки и увеличение используют прежний маршрут.
- GET `.../images/:fileGuid?version=:snapshot&preview=small|list` проверяет прежний
  admin-доступ, отсутствие employee-preview, принадлежность file GUID товару/снимку.
  Запрос только читает готовые байты и проверяет SHA256; FTP и декодер не вызываются.
  `no-store` сохраняется: отзыв доступа не ослабляется ради браузерного кэша.
- Переключение через `meta.thumbnailsReady` происходит после первого полного прохода
  всех путей снимка, при наличии хотя бы одного готового фото. До этого сохраняется
  прежняя выдача. Отсутствие миграции также не ломает существующий каталог.
- Отсутствующий/повреждённый/превысивший лимиты источник имеет явный результат
  `unavailable`, а не вымышленное фото. В интерфейсе действует прежняя заглушка.
  Временный сетевой сбой не объявляется доказанным отсутствием файла на FTP.

## Выпуск и ручная подготовка

Merge/deploy и production-миграция требуют согласования выпуска этого PR.
Автодеплой остаётся выключенным. Один законченный PR, один ручной deploy.

После согласования:

1. Зафиксировать production SHA, текущий снимок/число товаров и неизменность исходных
   записей; проверить резервную копию БД. Сверить pending migrations: только 085.
2. Выполнить один ручной deploy согласованного SHA и применить только добавочную
   миграцию 085. До подготовки старый механизм фотографий остаётся рабочим.
3. В консоли контейнера: `MALLOC_ARENA_MAX=2 node --expose-gc --max-old-space-size=64 --max-semi-space-size=1 dist/cli/internal-catalog-thumbnails.js --max-files=3`.
   Это dry-run: чтение/декодирование источников без записи миниатюр.
4. Небольшой apply: `MALLOC_ARENA_MAX=2 node --expose-gc --max-old-space-size=64 --max-semi-space-size=1 dist/cli/internal-catalog-thumbnails.js --apply --max-files=3`.
   Проверить два размера через авторизованный API и независимое подключение к БД.
5. Полный проход:
   `MALLOC_ARENA_MAX=2 node --expose-gc --max-old-space-size=64 --max-semi-space-size=1 dist/cli/internal-catalog-thumbnails.js --apply --max-files=10000`.
   При ограничении/прерывании повторить вручную: готовые проверяются и пропускаются.
6. Один отдельный ручной повтор временно недоступных источников:
   `MALLOC_ARENA_MAX=2 node --expose-gc --max-old-space-size=64 --max-semi-space-size=1 dist/cli/internal-catalog-thumbnails.js --apply --retry-failed --max-files=10000`.
   Не повторять бесконечно. Сохранить итоговые ready/unavailable/bytes и список
   затронутых товаров для проверки источников.
7. Обновить страницу. Проверить `thumbnailsReady`, реальные URL `preview=small/list`,
   поиск, размеры, detail/увеличение, mobile 375px и desktop 1440px. Сравнить исходные
   GUID/записи и число товаров до/после. Проверить, что выдача миниатюр не обращается
   к FTP; cold/warm измерения делать отдельно, не обещать коэффициент ускорения.

CLI удерживает отдельную advisory lease, использует одно последовательное
FTP-соединение с переподключением после сбоя. Лимиты: 45 минут/запуск,
8GiB полученных исходников, максимум 10000 попыток; не более 256MiB производных
для одного снимка/рецепта. Исходные ограничения байтов/пикселей/форматов сохраняются.
Смена активного снимка останавливает публикацию результатов; миниатюры разных
снимков не смешиваются. Код завершения 2 означает ограниченный проход или наличие
недоступных источников, не успешную подготовку всех фото.

## Progressive JPEG и временные ошибки

Этот блок не требует новой миграции. Миграцию 085 повторно не применять:
перед выпуском сверить её уже установленный статус. Сам merge не разрешает
production-подготовку, расписание, импорт или изменение настроек окружения.

Каталожный тракт после прежних проверок формата/байтов/пикселей преобразует
progressive JPEG в последовательный JPEG короткоживущим `/usr/bin/jpegtran`.
Обычные загрузки остаются на прежнем `processImageToPreview`.
Docker production-слой устанавливает `libjpeg-turbo-utils`; при отсутствии
исполняемого файла обработка откладывается, а не возвращается в опасный декодер.
Согласно [документации libjpeg-turbo](https://raw.githubusercontent.com/libjpeg-turbo/libjpeg-turbo/main/doc/usage.txt),
без переключателей преобразования jpegtran формирует baseline JPEG,
`-copy all` сохраняет дополнительные маркеры, `-strict` делает предупреждения
фатальными, а `-maxmemory 152m` задаёт 152000000 байт для менеджера памяти библиотеки.
Это не ОС-лимит полного RSS процесса.

Используется один переиспользуемый буфер до 24 MiB, без промежуточных файлов.
Одновременная тяжёлая обработка блокируется локально и PostgreSQL advisory lease
718332021. Блокировка удерживается до завершения Sharp-потребителя буфера:
следующий запрос не может перезаписать вход ещё работающего декодера.
Оригинал не меняется; ICC/EXIF сохраняются на промежуточном JPEG, ориентация
применяется при подготовке WebP, EXIF в производные не переносится.
Дочерний процесс запускается без shell, с фиксированными аргументами и без
FTP/DB-credentials в окружении.

Перед запуском оценивается память DCT-коэффициентов с запасом. Каждые 20 мс
проверяются RSS Node.js и нативного процесса (по 160 MiB), доступная память
(не менее 64 MiB); таймаут нативной стадии 10 секунд.
Берётся минимум MemAvailable и `process.availableMemory()`, если API доступен:
[Node.js определяет его как свободную память, доступную процессу](https://nodejs.org/api/process.html#processavailablememory).
Это sampled watchdog, не жёсткая гарантия отсутствия краткого превышения между
измерениями и не замена внешнему production-контролю/cgroup.

Только ручная CLI-подготовка устанавливает свой `UV_THREADPOOL_SIZE=1`
до загрузки модулей, `sharp.concurrency(1)` и `sharp.cache(false)`.
Она запускается с явным `--expose-gc --max-old-space-size=64 --max-semi-space-size=1` и вызывает
GC перед следующим файлом, после завершения прошлой обработки. Без expose-gc
CLI откажется начинать работу. Переменные Timeweb и глобальные настройки
работающего HTTP-процесса не меняются; GC в HTTP принудительно не вызывается.
В команде задаётся `MALLOC_ARENA_MAX=2` только для этого процесса:
на локальном glibc-стенде без него RSS рос даже при стабильном объёме живых
ArrayBuffer. Аллокатор production-образа отличается: локальный результат не
подменяет измерение в контейнере и не гарантирует ту же память.

Нехватка памяти, недоступная lease/база, отсутствие jpegtran, таймаут,
переполнение/таймаут очереди, оборванный FTP и сетевые ошибки дают
`CATALOG_IMAGE_DEFERRED`. Они не попадают в отрицательный кэш и не записывают
`unavailable`: подготовка прекращается с освобождением lease, файл остаётся
pending. Авторизованный HTTP-запрос после прежних проверок доступа и привязки
получает 503 `IMAGE_RETRY_LATER`, `Retry-After: 3`, без внутренних путей/ошибок.
Завершённый отрицательный ответ FTP 550, полный повреждённый источник и
прежние нарушения лимитов остаются `unavailable`. 550 означает невозможность
получить файл этим запросом, не доказательство его физического отсутствия.

### Локальная проверка

Тесты выполняются только на synthetic данных и отдельной локальной test-БД:
helper интеграционных тестов удаляет схему. Production URL запрещён.

`npm run build` и затем
`node scripts/verify-catalog-progressive-memory.mjs --iterations=10`.
Скрипт не читает БД/FTP: создаёт детерминированные JPEG 2438×5813 и 4000×6000,
progressive 4:4:4, не более 8 MiB. В отдельных Node-процессах сравнивает
прежний JPEG-тракт и новый, с одинаковыми ограничениями CLI, свежей копией
входа и GC перед каждой итерацией. Проверяет два размера WebP, отсутствие EXIF,
неизменность входа. Замеряет kernel maxRSS родителя, sampled RSS дочернего
процесса и их одновременную сумму с интервалом 5 мс. Сумма включает только
обработчик и его потомков, не работающий HTTP-сервер.

Итоговая локальная серия на Node 22.23.5, по 10 обработок каждого размера
в отдельном процессе на вариант (MiB, округление до десятых):

| Вход, байты | Размер | Прежний JPEG-тракт: Node | Новый: Node | Новый: native | Новый: одновременная сумма |
| --- | --- | ---: | ---: | ---: | ---: |
| 5660509 | 2438×5813 | 319.6 | 120.8 | 83.4 | 204.2 |
| 8083488 | 4000×6000 | 263.1 | 137.8 | 139.7 | 277.5 |

Оба варианта сравнивались при одинаковых `UV_THREADPOOL_SIZE=1`,
`MALLOC_ARENA_MAX=2`, `--expose-gc --max-old-space-size=64 --max-semi-space-size=1`,
`sharp.cache(false)`/`sharp.concurrency(1)`. «Прежний» здесь означает прежний
путь JPEG-декодирования под этими же параметрами, не повтор production-запуска.
Простые варианты с GC/буфером без ограничения арен не прошли длинную серию
24 Мп: измерения выше не распространяются на другие параметры аллокатора.
Сумма не включает HTTP-сервер или измеряющий процесс.

Сборка успешна; 52 targeted unit и 28 integration тестов прошли на Node 22.23.5.
Дополнительно проверены lossless-нормализация, ICC/EXIF, timeout/kill/release,
блокировка буфера до конца потребления и освобождение после ошибки,
межпроцессная PG lease, отсутствие отрицательного кэша и записи unavailable
при deferred, безопасный 503, сохранность записей, ботовая фильтрация и снимки.
Docker-сборка локально не проверялась: Docker в sandbox отсутствует.

### Новый production-проход

Требуется отдельное разрешение на один выпуск, пробу и последующую подготовку.
Без согласования эти команды не запускать. Предыдущие разрешения на пробы
не распространяются на этот выпуск.

1. Зафиксировать SHA, snapshot, ready/unavailable/pending, исходные GUID/хэши
   записей, RAM, oom_kill и отсутствие подготовки. Сверить установленную 085.
2. Один ручной deploy согласованного SHA; проверить health/ready и ЛК.
   Проверить наличие jpegtran. При проблеме остановиться: новый deploy,
   restart, rollback или повторная проба не разрешены автоматически.
3. Один apply на 3 pending-фото через настоящий CLI, с внешним наблюдением
   за Node.js, потомками и общим ресурсом приложения. Не ограничиваться RSS
   родителя: коэффициенты JPEG теперь находятся в дочернем процессе.
   При RSS любого процесса >160 MiB, сумме обработчика с потомками >288 MiB,
   доступной RAM <96 MiB, росте oom_kill или деградации HTTP прекратить всю
   группу обработки. После остановки не перепробовать автоматически.
4. Только при успешной пробе и отдельном/условном разрешении продолжить
   последовательными ограниченными CLI-проходами, без расписания/нового worker.
   Готовые пропускаются. Один отдельно разрешённый `--retry-failed` нужен для
   прежних unavailable: новый код не меняет старые статусы задним числом.
5. Временный сбой оставляет pending: зафиксировать причину/ресурсы и не
   объявлять очередь законченной. Превышение лимитов формата/ресурсов требует
   решения по конкретным источникам, а не скрытого снятия защиты.
6. Зафиксировать итоговые счётчики и сохранность оригиналов/товаров,
   проверить `thumbnailsReady`, small/list, detail/zoom в ЛК и получение
   фото в обоих ботах. Telegram/MAX отправки проверять в согласованных чатах.
   Нулевой pending сам по себе не означает «все фото есть»: каждый оставшийся
   unavailable требует отдельной классификации и сверки с источником обмена.
