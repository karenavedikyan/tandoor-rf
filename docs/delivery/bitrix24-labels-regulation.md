# Регламент меток клиентов для задач Bitrix24 (R2.2)

**Этап:** R2.2 · локальный пилот  
**Дата:** 2026-09-30  
**Production:** метки и кэш задач **не включать** без отдельного согласования

## 1. Назначение

Метка связывает **одну задачу Bitrix24** с **одним подтверждённым объектом ЛК**. Метка не является правом на просмотр задачи и не заменяет серверные проверки доступа.

## 2. Формат метки (единственный допустимый на первом запуске)

| Тип объекта | Префикс | Пример |
|-------------|---------|--------|
| Холдинг | `#LK_H_` | `#LK_H_000123` |
| Юрлицо | `#LK_J_` | `#LK_J_000456` |
| Торговая точка | `#LK_T_` | `#LK_T_000789` |

Правила:

- латинские заглавные буквы `H`, `J`, `T`;
- ровно **шесть** цифр (`000001` … `999999`);
- **`000000` запрещён**;
- примеры выше — **не реальные объекты**.

Метку выдаёт **сервер ЛК**. Код неизменяем, не переиспользуется и **не зависит** от названия клиента.

## 3. Подтверждение объекта

- Метка выдаётся только для объекта, зарегистрированного в `bitrix24_confirmed_objects`.
- **`guid_client` не считается** автоматически холдингом, юрлицом или торговой точкой.
- Для неподтверждённых объектов UI показывает: «Привязка ожидает подтверждения данных 1С».
- POST `/api/clients/:guid/bitrix24/label` поддерживает `holding`, `legal_entity`, `outlet` (query/body `objectType`) при подтверждённом объекте.

## 4. Где читать метку

- **Только** поле `DESCRIPTION` задачи Bitrix24.
- **Не** читать из заголовка, комментариев, штатных тегов Bitrix24.
- HTML/BBCode в описании **не исполняются**; метка извлекается после безопасного удаления разметки.

## 5. Правила привязки

| Ситуация | Поведение |
|----------|-----------|
| Одна метка в описании, код в реестре | `confirmed` |
| Повтор той же метки в описании | дубликат не создаётся |
| Разные метки в одном описании | `conflict`, автопривязка **не выполняется** |
| Метка не в реестре | `pending_confirmation` |
| Нет метки | `unresolved` |

Одна задача — один объект. Поиск по названию, телефону, адресу или ФИО **запрещён**.

## 6. Операции API

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/api/clients/:guid/bitrix24/label` | просмотр существующей метки (**не создаёт**) |
| POST | `/api/clients/:guid/bitrix24/label` | выдача метки (CSRF + auth) |
| GET | `/api/clients/:guid/bitrix24/tasks` | опубликованные задачи объекта (с проверкой прав) |

## 7. Синхронизация

- CLI: `npm run bitrix24-sync -- --bitrix-user-id <ID>` — **dry-run по умолчанию**;
- запись: `--apply`;
- область: задачи **одного** `RESPONSIBLE_ID`, не весь портал;
- транспорт R2.1 (SSRF, pinned HTTPS, pagination, PARTIAL);
- ключ кэша: `portal_id + task_id`;
- обновления идемпотентны; старая версия не перезаписывает новую по `changed_at`;
- **нет** фонового запуска при старте приложения, по расписанию или при открытии карточки.

## 8. Публикация кэша и права

До согласования production-политики:

```bash
BITRIX24_CACHE_PUBLISH_ENABLED=false   # по умолчанию
BITRIX24_CACHE_ACCESS_TTL_MS=0
```

Включение требует явного положительного TTL. Просроченное подтверждение связи сотрудника с порталом **не** позволяет бесконечно показывать старые задачи.

Перед показом задачи сервер проверяет:

1. доступ сотрудника к объекту ЛК;
2. подтверждённую связь `users.id` ↔ Bitrix user ID портала;
3. допустимую аудиторию задачи (ответственный = связанный Bitrix user);
4. актуальность подтверждения доступа.

Webhook-владелец **не** расширяет права конечного сотрудника. Роль РОПа и замещение ассистентом **не** открывают автоматически всё содержимое задач.

## 9. Временная защита пилота

`BITRIX24_PILOT_TASK_IDS` — **обязательный** список task ID при включённой публикации (`BITRIX24_PILOT_ALLOWLIST_REQUIRED=true` по умолчанию). Пустой список = задачи не показываются. Рекламации и внутренняя переписка **не публикуются** до отдельной проверки способа их отделения.
