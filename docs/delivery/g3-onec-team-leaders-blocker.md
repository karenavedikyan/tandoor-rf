## 1. Что подтверждено в коде и контракте

### Источник членства в группе

| Поле | Файл | Семантика |
|------|------|-----------|
| `guid_team` | `/LC/clients/all_employees.json` → `onec_wholesale_employee_roster.guid_team` | UUID группы; **ключ членства** сотрудника |
| `name_team` | тот же путь | Только отображение; **не** ключ |

Парсер: `src/onec-clients/employee-roster.ts` (`validateOptionalUuidField(raw, "guid_team")`).  
Семантика apply: `src/onec-clients/roster-field-values.ts` — «guid_team defines membership; name_team is display-only».

Группировка в UI G2: `src/clients/org/onec-teams-repository.ts` — `GROUP BY guid_team`, без поля руководителя.

### Чего **нет** в принятом контракте roster

В `WholesaleEmployeeRecord` и upsert **нет** полей, связывающих `guid_team` с `guid_manager` руководителя группы:

- нет `guid_team_leader`, `is_team_leader`, `leader_manager`, `guid_head_of_team` и т.п.;
- `raw_json` сохраняет неизвестные ключи, но **ни один** ключ руководства группы не читается, не валидируется и не попадает в колонки БД.

Полный перечень **разбираемых** полей roster — см. `toEmployeeRecord()` в `employee-roster.ts`.

### Не путать с РОП клиента

`guid_head_of_the_sales_department` / `name_head_of_the_sales_department` — поля **карточки клиента** (`all_clients.json`, extended snapshot), семантика **РОП отдела продаж** по клиенту/ТТ.  
Это существующий scope org-structure (`src/clients/org/assignment-sql.ts`), **не** руководитель группы сотрудников из `guid_team`.

Вывод: **явной GUID-связи `guid_team` → руководитель группы в текущем обмене нет.**

## 2. Вопрос специалисту 1С (один, с предлагаемым контрактом)

**Вопрос:** как в выгрузке ОПТ однозначно передать **GUID сотрудника-руководителя** для каждой группы с идентификатором `guid_team` (тот же UUID, что уже приходит в строках `all_employees.json` у участников группы)?

**Ограничения ЛК:**

- руководство и членство **независимы** (один человек может быть и руководителем, и участником той же `guid_team` без дубля строки в UI);
- **запрещено** выводить руководителя из `name_team`, ФИО, должности (`post`) или эвристик «один на группу»;
- руководитель — только `guid_manager` существующей строки roster (или явная ссылка на него);
- при 0 или >1 руководителе на группу — **проблема данных**, без выдачи прав.

**Предлагаемый контракт (на выбор 1С, нужен один зафиксированный вариант):**

**Вариант A — флаг на строке сотрудника (предпочтительно, если данные уже в справочнике сотрудника):**

```json
{
  "guid_manager": "<uuid>",
  "name_manager": "...",
  "guid_team": "<uuid группы>",
  "name_team": "...",
  "is_team_leader": true
}
```

Правила: для каждой `guid_team` в файле **ровно один** `is_team_leader: true` среди строк с этой `guid_team`; значение `guid_manager` этой строки = руководитель группы. Отсутствие ключа = не руководитель. Явный `false` = не руководитель.

**Вариант B — отдельный справочник групп в том же JSON-массиве или отдельном файле:**

```json
[
  {
    "guid_team": "<uuid>",
    "name_team": "...",
    "guid_team_leader": "<guid_manager руководителя>"
  }
]
```

Правила: `guid_team_leader` обязан совпадать с `guid_manager` одной из строк roster; при нарушении — ошибка валидации выгрузки или явный код проблемы в ответе 1С.

**После ответа:** обновить `employee-roster.ts`, миграцию (если нужны колонки), `import-runbook.md`, затем UI/API G3 по этому документу.

## 3. План реализации после подтверждения (не начат)

Переиспользовать без второго механизма доступа:

| Компонент | Переиспользование |
|-----------|-------------------|
| Портфели | Ответственные GUID клиента/ТТ (`buildClientScopeSql`, org filters) |
| Навигация | URL/state как org-structure: `view=teams`, `teamSource=onec`, drill-down |
| Счётчики | DISTINCT GUID клиентов/ТТ, не сумма пересечений |
| РОП | Существующий server scope + **явный** переключатель источника команд (по умолчанию — текущий ROP tree) |
| Preview | Тот же `AccessContext`, без расширения прав ROA/assistant |

Минимальная приёмка (локальная БД + browser) — по задаче G3 после появления поля руководства.
