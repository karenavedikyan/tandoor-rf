# R2.4: проверка существующих сводок рекламаций

Проверка 01.10.2026 по коду main `5390f302a53fb3606431eba42c8a9e5b80fd97fa` и локальной тестовой БД. Живые рекламации, действующая метка отдела и публикация в клиентский ЛК в эту проверку не входили.

## Итог

Основа для безопасного отображения сводок существует. Сквозной путь публикации специалистом из Битрикс24 и представление рекламаций ещё не реализованы; R2.4 и весь R2 не закрыты.

## Переиспользовать

| Механизм | Проверено |
|----------|-----------|
| Хранение сводки | `bitrix24_task_summary_publications`: разрешённый текст, автор публикации, дата, отзыв, точная привязка к порталу/задаче/объекту |
| Права и привязка | Без публикации сводка скрыта; чужая привязка не разрешает чтение; действуют права на клиента и актуальность связи сотрудника/кэша |
| Отображение | Общая очередь и карточка умеют показывать `summary`: разрешённый текст и подтверждённого ответственного |
| Ограничение данных | Summary не содержит внутреннего названия, ссылки на полную задачу, срока или чек-листа; поиск не использует скрытое название |
| Общие действия | Личная отметка «Связаться с ответственным» уже существует; не заменяет статус задачи |
| Дедупликация | Общая очередь использует `portal_id + task_id`, а не число карточек или комментариев |

Основания в коде: [проверка доступа](../../src/bitrix24/tasks/work-access.ts), [чтение активной публикации](../../src/bitrix24/tasks/work-repository.ts), [DTO сводки](../../src/bitrix24/tasks/task-work-response.ts), [пакетное чтение](../../src/work/batch-context.ts).

## Только недостающие части

1. **Получение публикации из Битрикс24.** Сейчас сводка читается из административно заполненной таблицы; рабочего обработчика публикации/обновления/отзыва из метки специалиста нет. Транспорт разрешает только `user.get`, `tasks.task.list`, `task.checklistitem.getlist`; комментарии не читаются. Не расширять методы или scope без конкретного согласованного сценария.
2. **Контракт публикации: уточнение после аудита.** Владелец утвердил `#орк` в описании задачи: существующая метка определяет клиента, весь текст после единственного `#орк` до конца описания становится сводкой. Текст до метки, комментарии и вложения не публикуются. Удаление метки снимает публикацию после успешной синхронизации; несколько меток или пустой текст блокируют публикацию. Отдельный блок `[ЛК]` не нужен. Сохраняется необходимость проверить полномочия публикации: хэштег не удостоверяет автора.
3. **Область синхронизации специалистов.** Чтение задач фильтруется по ответственному Битрикс24. Проверить, попадают ли ответственные отдела рекламаций в подтверждённую область; не считать подключение менеджеров достаточным и не расширять область автоматически.
4. **Статус сводки.** Сейчас summary получает общий технический статус задачи из кэша. Это не отдельный опубликованный специалистом статус рекламации; согласовать допустимые значения и источник, не выдавать одно за другое.
5. **Представление и счётчик.** Вкладка «Рекламации» пока заглушка. Подключить разрешённое представление тех же задач после подтверждения классификации; считать уникальные доступные обращения, не все задачи и не комментарии. Не создавать второй реестр/процесс.
6. **Жизненный цикл публикации.** После реализации проверить изменение/удаление метки, отзыв публикации, смену клиента и ответственного, ошибки чтения, устаревание и конкурирующие синхронизации. Не показывать старую сводку как текущую после неуспешной проверки её допустимости.

## Следующий шаг

Формат утверждён владельцем после аудита: см. [правило `#орк` в плане R2](./release-plan.md#r2--моя-работа-и-общий-контекст). Подготовить один ограниченный промпт на импорт разрешённой сводки, её обновление/отзыв и представление существующих задач; не запрашивать прежний хэштег как блокер проектирования. Для сквозной приёмки потребуется реальная задача в согласованной области и проверка полномочий специалиста. Новое правило ещё не реализовано; результаты 31 теста выше относятся к существующей основе, не к парсеру `#орк`.

Код приложения, права, webhook, данные production, импорт 1С и расписание не изменялись. Деплой для результатов этой проверки не нужен.
