### Три измерения доступа (не сводить к одному флагу)

| Измерение | Вопрос | Пример |
|-----------|--------|--------|
| **1. Роль** | Какие **действия** разрешены независимо от конкретного клиента | просмотр, экспорт, создание замещения, согласование |
| **2. Область доступа** | Какие **клиенты/объекты** доступны по постоянным назначениям | свои клиенты менеджера, команда РОП, ТТ regional |
| **3. Замещение** | **Временное** основание доступа к **выбранным** объектам | delegation ASST-1 → C1 на период; не заменяет роль |
| **4. Поля (В)** | Какие **категории данных** видны внутри разрешённого объекта | контакты, коммерция, финансы, служебные ID |

Замещение **дополняет**, но не подменяет роль и постоянную область. Координатор **не** становится замещающим менеджером автоматически.

## Рекомендуемая целевая модель (предложение — **на согласование**)

**Предложение для R1.3/R4.3:** отдельные системные роли `assistant` и `coordinator` **плюс** таблица записей замещений (`delegations`) и связанные таблицы назначений.

| Компонент | Назначение | Статус |
|-----------|------------|--------|
| Роли `assistant`, `coordinator` | потолок **действий** (не область клиентов) | **предложение**; потребует migration enum |
| `access_grants` | постоянная **область** (менеджер, regional, …) | **предложение**; потребует migration |
| `delegations` | **временное** основание для assistant | **предложение**; потребует migration |
| `user_onec_employee_links` | связь user ↔ ID сотрудника 1С | **предложение**; потребует migration |

> R1.3-prep **не реализует** перечисленное. Утверждение «без migration» для замещений **неверно**: таблица замещений — изменение схемы БД.
> **Не рекомендуется:** выдавать ассистенту роль `manager` ради обхода migration — смешивает HR-роль, область и замещение.

## Сводная матрица по ролям

Ниже — **целевая модель** (требование + предложение). «Кто выдаёт / срок / аудит» — [access-rules.md §6–§7](./access-rules.md).

### admin — технический администратор

| Измерение | Реализовано сейчас | Целевая модель (предложение) |
|-----------|-------------------|------------------------------|
| **Роль (действия)** | read clients API (4 GET) | users, import runbook, диагностика, журналы; **не** коммерческие решения |
| **Область** | все клиенты (admin-only API) | технический доступ ко всем данным ЛК для обслуживания |
| **Замещение** | n/a | admin **не** получает замещение «как менеджер» по умолчанию |
| **Поля** | все поля snapshot | все + служебные; запись в 1С **запрещена** |
| **Запрещено** | — | бизнес-назначения без решения уполномоченного руководителя и аудита; «admin override» клиентских назначений |

> Текущий admin-only режим — **реализовано**, не целевая модель для всех сотрудников.

### director — директор по продажам

| Измерение | Целевая модель |
|-----------|----------------|
| **Роль** | просмотр, аналитика, согласование исключений (**на согласование:** границы) |
| **Область** | **предложение:** вся **подтверждённая** sales-база компании |
| **Замещение** | n/a по умолчанию |
| **Поля** | контакты, коммерция (R1.1+), агрегаты по холдингу; финансы — R4 |
| **На согласование** | подтверждение должности «директор по продажам» = роль `director` |

> **Не смешивать** с `admin`.

### rop — руководитель отдела продаж (**требование**)

| Измерение | Целевая модель |
|-----------|----------------|
| **Роль** | просмотр; корректировка доступов и **замещений в команде** (**на согласование:** без согласования director) |
| **Область** | клиенты **подтверждённой команды** |
| **Замещение** | инициирование/отзыв замещений менеджеров команды |
| **Запрещено** | клиенты чужих РОП; глобальные назначения |

### regional_manager (**требование**)

| Измерение | Целевая модель |
|-----------|----------------|
| **Роль** | просмотр; визит/витрина (R3) |
| **Область** | **только** подтверждённые назначения; город/территория **≠** доступ |
| **Запрещено** | соседние ТТ; финансы холдинга при доступе к одной ТТ |

### manager (**требование**)

| Измерение | Целевая модель |
|-----------|----------------|
| **Роль** | просмотр; копирование контактов; **инициирование замещения** по своим клиентам |
| **Область** | **только** своя подтверждённая база (user ↔ `employee_id` ↔ закрепление) |
| **Запрещено** | чужие клиенты (list, card, ID, search, filters, total, export); **повторное делегирование** ассистентом |

### marketer / analyst / category_manager (**предложение**)

Минимальные права под задачи роли; **не** вся база, **не** финансы, **не** управление доступом по умолчанию. См. предыдущую версию матрицы — без расширения scope.

### assistant — ассистент (**требование** + **предложение** роли)

| Измерение | Целевая модель |
|-----------|----------------|
| **Роль (предложение)** | системная роль `assistant`: рабочие действия **в scope замещения**; **без** управления доступами, повторного делегирования, прав admin/руководителя |
| **Область** | **только** через **действующие** записи `delegations` (может быть несколько одновременно) |
| **Замещение** | единственное основание доступа к чужим клиентам |
| **Поля** | рабочий контекст переданных объектов (данные, задачи R2, заказы R4, документы, условия, финансы **в scope**) |
| **После отзыва/окончания** | доступ **прекращается**; незавершённая работа → ведущему менеджеру (**≠** смена ответственного в B24) |
| **История** | сохраняется для **уполномоченных** (менеджер, РОП, audit); **ассистент без действующего доступа не читает** карточку/документы/задачи/вложения/историю с клиентскими данными |

### coordinator — координатор ассистентов (**требование** + **предложение** роли)

| Измерение | Предложение | На согласование |
|-----------|-------------|-----------------|
| **Роль (предложение)** | системная роль `coordinator` | create/approve/modify/revoke delegations; границы «своих» команд |
| **Область** | график замещений, загрузка, **минимальные** сведения о замещениях (кто, когда, статус) | **не** полные карточки клиентов по умолчанию |
| **Замещение** | **не** становится замещающим менеджером автоматически | отдельное замещение — только если оформлено как у assistant |
| **Поля** | метаданные delegations | клиентские поля — только при **отдельном** grant (**на согласование**) |

## Иерархия клиента (целевая, R1.2+)

```
Холдинг
├── Юрлицо A ── продажи (1С)
├── Юрлицо B
└── ТТ-1, ТТ-2, …  (связь с юрлицами — явная из 1С; не 1:1)
```

### Зафиксированные правила (**требование** + **предложение**)

| Правило | Статус |
|---------|--------|
| Доступ к **ТТ** не открывает соседние ТТ, другие юрлица, финансы холдинга | **требование** |
| Минимальные сведения родителя для **навигации** ≠ доступ к **карточке** родителя | **требование** |
| Общий `guid_holding` у строк snapshot **не расширяет** автоматически права менеджера | **требование** |
| Наследование от холдинга/юрлица вниз — **только** по явно утверждённой политике | **на согласование** |
| Новые дочерние объекты **не включаются** в замещение с **фиксированным списком** | **требование** |
| До согласования спорных правил — **не расширять** доступ | **требование** |
| Продажи по ТТ — **не** искусственное распределение агрегата холдинга | **требование** |

### Спорные правила (**на согласование** — до решения scope не расширять)

| ID | Вопрос |
|----|--------|
| Q-HIER-1 | Grant на юрлицо → все связанные ТТ или whitelist? |
| Q-HIER-2 | Менеджер на `guid_client` → будущие юрлица/ТТ того же холдинга? |
| Q-HIER-3 | Regional на ТТ → адрес доставки ≠ адрес ТТ? |
