## Сводная матрица по ролям

Ниже — **целевая модель R1.3** (требование + предложение). Колонки «кто выдаёт / срок / аудит» — см. [access-rules.md §4–§6](./access-rules.md).

### admin — технический администратор

| Ось | Реализовано сейчас | Целевая модель (предложение) |
|-----|-------------------|------------------------------|
| **А. Область** | все клиенты (admin-only API) | все данные ЛК для **технического** обслуживания: пользователи, импорт, диагностика, журналы |
| **Б. Действия** | полный CRUD API клиентов (read) | управление учётными записями, runbook импорта, просмотр ошибок; **не** бизнес-согласование коммерции |
| **В. Поля** | все поля snapshot | все поля + служебные идентификаторы; редактирование 1С **запрещено** |
| **Основание** | роль `admin` в БД | назначение владельцем / ИТ |
| **Запрещено** | — | выдача себе «рабочих» клиентских баз без аудита; подмена бизнес-роли director/РОП |

> **Важно:** текущий admin-only режим — **существующий**, не целевая модель для всех сотрудников.

### director — директор по продажам (системная роль)

| Ось | Целевая модель |
|-----|----------------|
| **А. Область** | **предложение:** вся **подтверждённая** клиентская база компании (все холдинги/юрлица/ТТ в scope продаж) |
| **Б. Действия** | просмотр, аналитика, согласование исключений; назначение/отзыв **не** на уровне ИТ-admin |
| **В. Поля** | контакты, коммерция (после R1.1), агрегаты продаж по холдингу; финансы — по политике R4 |
| **Основание** | роль + **подтверждение** соответствия должности «директор по продажам» системной роли `director` (**на согласование**) |
| **Запрещено** | техническое администрирование; автоматический доступ без явного mapping user↔1C |

> **Не смешивать** директора по продажам с `admin`.

### rop — руководитель отдела продаж

| Ось | Целевая модель (**требование**) |
|-----|--------------------------------|
| **А. Область** | клиенты **подтверждённой команды** (менеджеры, закреплённые за РОП) + их объекты иерархии |
| **Б. Действия** | просмотр; **корректировка доступов и замещений** в пределах команды; инициирование замещения |
| **В. Поля** | рабочий контекст команды: контакты, условия, задачи (R2), без финансов всей компании |
| **Основание** | назначение «РОП ↔ команда менеджеров» из 1С / кадрового справочника (**R1.3**) |
| **Запрещено** | клиенты чужих РОП; изменение глобальных назначений director/admin |

### regional_manager — региональный менеджер

| Ось | Целевая модель (**требование**) |
|-----|--------------------------------|
| **А. Область** | только клиенты/ТТ/юрлица по **подтверждённым назначениям**; город/территория **сами по себе не дают** доступ |
| **Б. Действия** | просмотр; фиксация визита/витрины (R3); поручения по своим объектам |
| **В. Поля** | контакты, ассортимент/витрина; **не** коммерция всего холдинга при доступе только к одной ТТ |
| **Основание** | явное назначение на объект (ТТ / юрлицо / холдинг) |
| **Запрещено** | «соседние» ТТ без назначения; агрегаты, раскрывающие финансы холдинга |

### manager — менеджер по продажам

| Ось | Целевая модель (**требование**) |
|-----|--------------------------------|
| **А. Область** | **только своя подтверждённая** клиентская база (`guid_manager` ↔ ID сотрудника 1С пользователя) |
| **Б. Действия** | просмотр; копирование контактов; инициирование замещения **только по своим** клиентам; поручения (R2) |
| **В. Поля** | контакты, адрес, телефоны, условия (R1.1+); реквизиты юрлица своих клиентов (R1.2); **не** чужая коммерция |
| **Основание** | назначение менеджера на клиента/объект в 1С |
| **Запрещено** | чужие клиенты (список, карточка, прямой ID, поиск, фильтры, total, экспорт) |

### marketer — маркетолог

| Ось | Целевая модель (**предложение**) |
|-----|----------------------------------|
| **А. Область** | **не** вся база; срезы по программам/кампаниям/холдингам из **явного списка** назначений |
| **Б. Действия** | просмотр разрешённых карточек; экспорт **только** согласованных полей |
| **В. Поля** | маркетинговые атрибуты, программы (R5); **без** финансов, долгов, персональных контактов вне scope |
| **Основание** | назначение владельцем / director на кампанию |
| **Запрещено** | управление доступами; полная клиентская база |

### analyst — аналитик

| Ось | Целевая модель (**предложение**) |
|-----|----------------------------------|
| **А. Область** | агрегированные срезы по **утверждённым** наборам (команда, регион, холдинг); без построчного доступа «ко всем» |
| **Б. Действия** | просмотр отчётов; экспорт агрегатов с **минимизацией** полей |
| **В. Поля** | обезличенные или агрегированные метрики; **не** телефоны/адреса без отдельного основания |
| **Основание** | назначение director/admin на аналитический scope |
| **Запрещено** | drill-down до карточки клиента вне scope; фильтры-справочники с чужими ID |

### category_manager — категорийный менеджер

| Ось | Целевая модель (**предложение**) |
|-----|----------------------------------|
| **А. Область** | клиенты/ТТ, где есть **подтверждённая** связь с категорией/ассортиментом (R3+) |
| **Б. Действия** | просмотр ассортимента, витрины, рекомендаций по категории |
| **В. Поля** | товарный блок, доля витрины; **без** финансов и коммерческих условий вне категории |
| **Основание** | назначение на категорию + объект |
| **Запрещено** | полная база; управление замещениями |

## Ассистент и координатор (отсутствуют в enum — варианты моделирования)

**Требование:** роли нужны по v1.1 (экраны 16, 18–20); в БД **не добавляются** в R1.3-prep.

| Вариант | Описание | Плюсы | Минусы |
|---------|----------|-------|--------|
| **V1. Новые роли** | `assistant`, `coordinator` в migration | явная семантика в JWT/сессии | изменение enum, миграции, все проверки |
| **V2. Назначения без роли** | пользователь с ролью `manager` или отдельной «служебной» + таблица `delegations` | гибкость, несколько замещений | сложнее UI и аудит |
| **V3. Пакет прав** | `user` + `permission_bundle=assistant` | разделение HR-роли и делегирования | два измерения в каждой проверке |

**Рекомендация (предложение):** **V2 + явный статус замещения** в R1.3/R4.3; роли `assistant`/`coordinator` — отдельная migration после согласования V1 vs V2.

### assistant — ассистент (целевая модель, **требование**)

| Ось | Правило |
|-----|---------|
| **А. Область** | **выбранные** клиенты/объекты на период замещения; может замещать **нескольких** менеджеров одновременно |
| **Б. Действия** | полный **рабочий** контекст по переданным клиентам: данные, задачи (R2), заказы/отгрузки (R4), документы, условия, финансы **в scope клиента**; **не** admin/руководитель |
| **В. Поля** | как у менеджера по переданным объектам; служебные ID — по политике |
| **Срок** | `starts_at` … `ends_at` (Europe/Moscow); по окончании/отзыве — **немедленное** прекращение |
| **После отзыва** | незавершённая работа → ведущему менеджеру; **история действий ассистента сохраняется** |
| **Запрещено** | права администратора; доступ вне списка замещения; **автоматическая** смена ответственного в Битрикс24 |

### coordinator — координатор ассистентов (**требование** + **на согласование**)

| Ось | Предложение | На согласование |
|-----|-------------|-----------------|
| **А. Область** | календарь замещений, загрузка ассистентов | доступ ко **всем** клиентским данным команды? |
| **Б. Действия** | планирование/редактирование замещений; отзыв; **не** автоматически просмотр карточек | может ли координатор **открывать** карточку клиента без замещения |
| **В. Поля** | метаданные замещений; клиентские поля — **только** если явно включено | минимальный vs расширенный профиль |

## Матрица: область × действие × поля (компактно)

| Роль | А: типичная область | Б: разрешённые действия | В: поля по умолчанию | В: требует отдельного основания |
|------|---------------------|-------------------------|----------------------|----------------------------------|
| admin | весь ЛК (тех.) | users, import, logs, read all | все + служебные | — |
| director | компания (sales) | read, approve exceptions | контакты, коммерция, агрегаты | финансы, PII вне sales |
| rop | своя команда | read, manage access/delegation в команде | контекст команды | финансы других РОП |
| regional_manager | назначенные объекты | read, visit/fix (R3) | контакты, витрина | коммерция холдинга при доступе к ТТ |
| manager | свои клиенты | read, copy contacts, delegate own | контакты, условия | чужие клиенты |
| marketer | кампании/программы | read scoped | маркетинг | контакты, финансы |
| analyst | агрегаты | read/export aggregates | метрики | построчные карточки |
| category_manager | категория × объект | read assortment | витрина, SKU | финансы |
| assistant | клиенты замещения | read/work as manager in scope | рабочий контекст | вне замещения |
| coordinator | замещения | plan/revoke delegations | метаданные замещений | карточки клиентов (**?**) |

## Иерархия клиента (целевая, R1.2+)

```
Холдинг
├── Юрлицо A ── продажи (1С)
├── Юрлицо B
└── ТТ-1, ТТ-2, …  (связь с юрлицами — явная из 1С; не 1:1)
```

| Уровень назначения | Видимость (**предложение**) | Наследование вниз | Наследование вверх / в сторону |
|--------------------|----------------------------|-------------------|--------------------------------|
| Холдинг | все юрлица и ТТ холдинга (если не ограничено политикой) | да, если не отозвано на дочернем | — |
| Юрлицо | это юрлицо + связанные ТТ (**на согласование:** все или только явно связанные) | к ТТ юрлица | **не** автоматически весь холдинг |
| ТТ | только ТТ + минимальный контекст родителя для навигации | — | **не** финансы всего холдинга; **не** соседние ТТ |

**Пересечение назначений:** доступ = **объединение** явных grant'ов минус explicit deny (**на согласование** приоритет deny).

**Продажи:** привязаны к юрлицам, агрегируются по холдингу; **не** распределяются достоверно по ТТ → не показывать фиктивную детализацию по ТТ.
