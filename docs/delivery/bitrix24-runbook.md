# Runbook: подключение Bitrix24 (R2.1 + R2.2)

**Этап:** R2.1 (диагностика) + R2.2 (метки и локальный кэш)  
**Production:** **не включать** без отдельного согласования

## 1. Что делает этот этап

- Проверяет конфигурацию incoming webhook **локально** (без сети).
- По явному запросу оператора читает **ограниченную** выборку задач **конкретного** Bitrix user ID.
- **Не сохраняет** задачи в БД, **не меняет** права, **не запускается** из web-сервера, login, health/readiness или cron.

## 2. Что нужно от администратора Bitrix24

1. Создать **incoming webhook** с scopes для [user.get](https://apidocs.bitrix24.com/api-reference/user/user-get.html) (`user` / `user_brief`) и [tasks.task.list](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-list.html) (`task`).
2. Зафиксировать **Bitrix user ID** сотрудника, для которого выполняется диагностика (не ID владельца webhook по умолчанию).
3. Передать webhook URL **только** через защищённое хранилище секретов или серверное окружение Timeweb — **не** в Git, PR, чат или `.env` в репозитории.

## 3. Переменные окружения

См. `.env.example`. Минимум для live-диагностики:

```bash
BITRIX24_ENABLED=true
BITRIX24_WEBHOOK_URL=https://<portal>.bitrix24.ru/rest/<user_id>/<webhook_token>/
# опционально:
# BITRIX24_PORTAL_HOST=<portal>.bitrix24.ru
```

## 4. Локальная разработка (файл `.env`)

```bash
npm run build
npm run bitrix24-probe:local
```

Live-диагностика локально:

```bash
npm run bitrix24-probe:local -- --live --bitrix-user-id <BITRIX_USER_ID>
```

Команды `*:local` читают `.env` через `--env-file`. Это **не** универсальная production-команда.

## 5. Серверное окружение Timeweb (env уже задан платформой)

```bash
npm run build
node dist/cli/bitrix24-probe.js
node dist/cli/bitrix24-probe.js --live --bitrix-user-id <BITRIX_USER_ID>
```

**Блокер:** интерактивная SSH/консоль на текущем размещении TW для операторского запуска **не подтверждена** этим PR. Фактически доступный способ one-off job / console уточняется у платформенного оператора. HTTP-endpoint или автозапуск при старте приложения **не добавляются** как обход.

## 6. Отчёт CLI

Содержит: `checkedAt` (ISO UTC), `portalId`, список проверок, число задач, полноту выборки, коды ошибок, недоступные возможности.

**Не содержит:** тексты задач, ФИО, email, телефоны, webhook token, произвольные `error_description` портала.

## 7. Отключение

1. Установить `BITRIX24_ENABLED=false` или удалить `BITRIX24_WEBHOOK_URL` из env.
2. При компрометации webhook — **отозвать** webhook в Bitrix24 и выпустить новый.
3. Перезапуск приложения **не обязателен** для отключения CLI; web-приложение не использует Bitrix24 в R2.1.

## 8. Интерпретация статусов

| Статус | Действие |
|--------|----------|
| `DISABLED` | Интеграция выключена — штатно для dev/test |
| `LOCAL_OK` | Конфигурация валидна; live-проверка не запускалась |
| `SUCCESS` | Live-выборка задач получена полностью в пределах лимитов |
| `PARTIAL` | Выборка обрезана лимитами — не считать полной синхронизацией |
| `AUTH_FAILED` / `FORBIDDEN` | Проверить webhook, scopes, user ID |
| `INVALID_USER` | Указанный Bitrix user ID не найден |
| `RATE_LIMITED` | Повторить позже; проверить лимиты портала |

## 9. R2.2 — метки и ручная синхронизация (локальный пилот)

### 9.1. Выдача метки

1. Подтвердить объект в `bitrix24_confirmed_objects` (после данных 1С).
2. Открыть карточку клиента → вкладка «Работа» → «Скопировать метку для Bitrix24».
3. Вставить метку **отдельной строкой** в описание задачи Bitrix24 (не в комментарии).

Формат: `#LK_H_000123` (холдинг), `#LK_J_000456` (юрлицо), `#LK_T_000789` (ТТ).  
Регламент: `docs/delivery/bitrix24-labels-regulation.md`.

### 9.2. Связь сотрудника с порталом

Запись в `bitrix24_employee_portal_links` (user ЛК ↔ Bitrix user ID). Без неё задачи не показываются, даже при наличии метки.

### 9.3. Ручная синхронизация

```bash
npm run build
# dry-run (по умолчанию):
npm run bitrix24-sync:local -- --bitrix-user-id <BITRIX_USER_ID>
# запись в локальный кэш:
npm run bitrix24-sync:local -- --bitrix-user-id <BITRIX_USER_ID> --apply
```

Область: задачи **одного ответственного**, не весь портал.

### 9.3.1. Диагностика кэша и привязок

```bash
npm run build
npm run bitrix24-diagnostics:local -- --bitrix-user-id <BITRIX_USER_ID>
```

Параметр `--bitrix-user-id` **обязателен**: журнал синхронизации ищется только по точной области `portal_id + bitrix_user_id`, общий журнал портала не возвращается.

### 9.3.2. Сводка задачи и «Связаться с ответственным»

- **Полная задача** (название, переход в Bitrix24) — только если ответственный Bitrix user совпадает с подтверждённой связью сотрудника-читателя.
- **Краткая сводка** для остальных членов команды клиента — только при явной записи в `bitrix24_task_summary_publications` (по умолчанию **закрыто**). Метка не даёт права публикации.
- ФИО ответственного показывается только при подтверждённой связи `bitrix24_employee_portal_links` ↔ `users`; иначе — «имя не подтверждено».
- Отметка «Связаться с ответственным» хранится в ЛК (`bitrix24_task_contact_actions`), не меняет задачу Bitrix24.
- Публикация сводки проверяется по точному `portal_id + task_id + object_type + object_guid`. При другой привязке старая сводка не видна.
- Неоднозначные, просроченные и неподтверждённые связи ответственного не используются для показа ФИО.
- Галочка личная: состояние и журнал меняются в одной транзакции, конкурентные запросы сериализуются по сотруднику/задаче/объекту. Повторное выставление или снятие безопасно; отсутствие `comment` не удаляет предыдущий комментарий.
- Комментарий вводится в ЛК только после явного выполнения действия; ввод текста сам по себе не ставит галочку. При ошибке сохранения интерфейс возвращает предыдущее состояние.
- Переход «Внутренние контакты» сейчас открывает почту подтверждённого сотрудника. Автоматического предоставления доступа к задаче и записи в Bitrix24 нет.
- Публикация сводок пока административная, без пользовательского редактора. Эта версия не публикует сводки автоматически и не расширяет пилот.

### 9.3.3. «Следующие действия» в обзоре клиента

- «Обзор» и «Работа» используют один ответ `/api/clients/:guid/bitrix24/tasks`, без отдельного источника прав, задач или галочек.
- В обзоре показаны до трёх незавершённых задач: просроченные, затем ближайшие по сроку. «Все доступные задачи» открывает вкладку «Работа».
- Счётчики включают только разрешённые сервером задачи. При неизвестном статусе или закрытом сроке выводится «нет данных» / «не менее N», не ложный ноль.
- Сводка не раскрывает внутренний срок задачи: `deadlineAt=null`, `isOverdue=null` для незавершённой задачи. Клиент не восстанавливает сроки из форматированного текста.
- Одна личная отметка сохраняется одинаково в обоих разделах. Завершение личного действия не исключает открытую задачу из списка.
- Кнопка «Обновить данные ЛК» повторно читает опубликованный кэш, а не запускает синхронизацию Битрикс24 или 1С. Ошибки, истёкшие права и устаревший кэш скрывают предыдущие задачи в обоих разделах.
- Чек-листы читаются в рамках разрешённого sync: прогресс в «Обзоре», раскрытие пунктов в «Работе», только для полной задачи. Summary не получает пункты или прогресс. Исходные пункты Битрикс24 из ЛК не изменяются; личная галочка остаётся отдельным действием.

### Ручная синхронизация карточки (PR24)

- Кнопка «Синхронизировать с Битрикс24» вызывает серверный POST. Область определяется сервером: карточка, подтверждённая связь сотрудника, ответственный и разрешённые задачи пилота.
- Для первого запуска без кэша допустимо прочитать метаданные задачи. До публикации и чтения чек-листа повторно проверяются привязка источника, текущие права и активность сотрудника. Запрос с чужой/неподтверждённой привязкой получает 403 без публикации новых данных и без загрузки чек-листа.
- При смене исходной привязки прежний снимок карточки снимается с публикации только при совпадении версии, чтобы запоздалый отказ не затронул более новое поколение кэша.
- Один PostgreSQL connection удерживает блокировки всего batch. При отказе на любом шаге ранее захваченные блокировки освобождаются; при ошибке unlock соединение уничтожается, а не возвращается в пул. Повторный release безопасен.
- Миграция `017_bitrix24_manual_sync_cooldown.sql` добавляет только таблицу cooldown. Интервал задаёт `BITRIX24_MANUAL_SYNC_MIN_INTERVAL_MS`, по умолчанию 30 секунд.
- После success, partial, failed и отказа доступа интерфейс перечитывает разрешённые данные ЛК. При HTTP-ошибке перечитывания нет ложного сообщения об успешном обновлении; старый прогресс не сохраняется на экране как актуальный.
- Кнопка «Обновить данные ЛК» остаётся чтением кэша. Открытие карточки не запускает обмен; 1С, расписания, права webhook и состав пилота не меняются.

### Рабочий режим (working mode)

По умолчанию `BITRIX24_TASKS_MODE=pilot`. Рабочий режим включается только при явной политике кэша:

```bash
BITRIX24_TASKS_MODE=working
BITRIX24_CACHE_PUBLISH_ENABLED=true
BITRIX24_CACHE_ACCESS_TTL_MS=3600000
BITRIX24_LINK_VERIFICATION_TTL_MS=86400000
BITRIX24_WORKING_MAX_TASKS_PER_SYNC=20
BITRIX24_WORKING_MAX_DISCOVERY_PAGES=5
BITRIX24_WORKING_MAX_DISCOVERY_PAGES_TOTAL=25
```

- Discovery: **один** bounded-обход `tasks.task.list` с `filter={RESPONSIBLE_ID}` (без `%DESCRIPTION`). Метки карточки проверяются на сервере через `extractLabelsFromDescription` и registry подтверждённых меток; `RESPONSIBLE_ID` повторно сверяется в каждой записи ответа.
- **Проверка реального портала (read-only, владелец):** `optovik.bitrix24.ru`, webhook backend. `tasks.task.list` с `filter={ID:1041697, RESPONSIBLE_ID:2, "%DESCRIPTION":"#LK_H_000001"}` и с `"%DESCRIPTION":"#LK_H_999999"` **оба** вернули задачу `1041697` — `%DESCRIPTION` фактически игнорируется. Discovery от него не зависит.
- Официальный REST [`tasks.task.list`](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-list.html) документирует шаблонный поиск только для `TITLE`. Mock-тесты имитируют игнорируемый `%DESCRIPTION`.
- Общий бюджет страниц discovery — `BITRIX24_WORKING_MAX_DISCOVERY_PAGES_TOTAL` на всю операцию (не N×maxPages на метку).
- Перед sync выполняется `user.get` для обновления `last_verified_at`; `confirmed_at` не истекает по TTL кэша.
- Cooldown/lock: сотрудник+карточка (`018`) и task-locks (`017`).
- Массовая регистрация меток из снимка 1С (dry-run по умолчанию):

```bash
npm run bitrix24-labels-bootstrap:local          # dry-run (по умолчанию)
npm run bitrix24-labels-bootstrap:local -- --apply --actor=<user-uuid>  # только после проверки плана
```

При конфликте привязки карточки apply не выполняет изменений; audit фиксирует `conflict`.

**Откат:** `BITRIX24_TASKS_MODE=pilot` и прежний `BITRIX24_PILOT_TASK_IDS`.

### 9.4. Публикация кэша в UI (только после согласования)

```bash
BITRIX24_CACHE_PUBLISH_ENABLED=true
BITRIX24_CACHE_ACCESS_TTL_MS=3600000   # явный положительный TTL
BITRIX24_PORTAL_PUBLIC_URL=https://<portal>.bitrix24.ru
# пилот (по умолчанию):
BITRIX24_TASKS_MODE=pilot
# BITRIX24_PILOT_TASK_IDS=9001,9002
```

## 10. Что runbook не делает

- Не включает production-синхронизацию по расписанию
- Не создаёт задачи в Bitrix24
- Не меняет импорт 1С
- Не запускает sync при открытии карточки или старте приложения

**Проверка на реальном портале не выполнена** в рамках CI и автотестов этого PR.
