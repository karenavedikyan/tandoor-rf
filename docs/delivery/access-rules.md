- Два менеджера **не видят** чужие записи (в т.ч. прямой API).
- РОП видит **свою** команду.
- Региональный — **только по назначениям**, не по городу.
- Замещение ассистентом — по датам, с возвратом работы (экраны 18–20 → R4).
- Права на **сервере** (экран 24).
- user ↔ стабильный ID сотрудника 1С — **не по ФИО/телефону/email**.

## 2. Три измерения: роль, область, замещение

| Измерение | Что определяет | Источник (целевой) |
|-----------|----------------|---------------------|
| **Роль** | потолок **действий** (просмотр, экспорт, создать delegation, …) | `users.role` (+ будущие assistant/coordinator) |
| **Область доступа** | какие объекты видны **постоянно** | 1С-назначения → `access_grants` |
| **Замещение** | **временный** доступ assistant к **выбранным** объектам | `delegations` |

Координатор планирует замещения; **не** получает права замещающего менеджера без отдельной записи delegation.

## 3. Источники назначений

| Источник | Что задаёт | Приоритет | Статус |
|----------|------------|-----------|--------|
| **1С: справочник сотрудников** | стабильный `employee_id` | первичный | ⏸ Q7, Q10 |
| **1С: закрепление** | менеджер на клиенте/объекте | первичный для scope | частично: `guid_manager` на строке |
| **1С: оргструктура** | РОП ↔ команда, regional ↔ объекты | первичный | ❌ R1.2 / Q8 |
| **ЛК: access_grants** | marketer/analyst scope | вторичный + audit | 📋 |
| **ЛК: delegations** | временный scope assistant | вторичный + audit | 📋 R4.3 |
| **Статус учётной записи** | active/disabled/invited | блокирующий | ✅ |

### 3.1 Связь user ↔ сотрудник 1С (**требование**)

| Правило | Описание |
|---------|----------|
| PK связи | подтверждённый ID сотрудника 1С ↔ `users.id` |
| **Запрещено** | auto-link по ФИО, email, phone, `name_manager` |
| Нет / конфликт связи | доступ к клиентским данным **закрыт** |
| `disabled` в ЛК | отказ auth; **старые сессии** недействительны на **следующем** запросе |

### 3.2 Увольнение и изменение назначений

**Два независимых канала:**

| Канал | Поведение (целевое) |
|-------|---------------------|
| **Блокировка в ЛК** (`disabled`, отзыв grant/delegation) | прекращение доступа на **следующем** серверном запросе, включая старые сессии |
| **Изменение в 1С** (увольнение, смена закрепления) | зависит от **фактической частоты обмена**; **не** гарантирует мгновенный отзыв |

**Предложение (на согласование):**

- До подтверждения возможностей 1С — **немедленная ручная блокировка** уполномоченным admin.
- **Ночная синхронизация не является** безусловно безопасным решением и **не** рекомендуется как единственный механизм отзыва после увольнения в 1С.
- Допустимая **задержка обмена** — **на согласование** с владельцем и 1С-специалистом.
- **Не заявлять** наличие webhook или кадровых выгрузок без проверки (Q-SYNC-1).

**Зависимые замещения:** при изменении закрепления клиента или отзыве полномочий выдавшего доступ — **пересмотр** связанных `delegations`. Старое замещение **не должно** обходить отзыв исходных полномочий.

## 4. Бизнес-правила по ролям

### 4.1 Менеджер (**требование**)

- Своя **подтверждённая** база; **не** видит чужих (list, card, ID, search, filters, total, export).
- Инициирует замещение **только** по своим клиентам.

### 4.2 Региональный (**требование**)

- Только **подтверждённые** назначения; город/территория **≠** доступ.
- ТТ **не** раскрывает соседей, другие юрлица, финансы холдинга.

### 4.3 РОП (**требование**)

- Своя команда и её клиенты; корректировка access/delegation **в команде** (**на согласование:** нужно ли согласование director).

### 4.4 Директор по продажам (**предложение**)

- Sales-база компании; **≠ admin**; подтверждение должности (**на согласование**).

### 4.5 Ассистент (**требование**; роль — **предложение**)

- Доступ **только** через **действующие** delegations.
- Рабочий контекст в scope; **без** управления доступами, **повторного делегирования**, прав admin/руководителя.
- Несколько замещений → scope = **union**; отзыв одного → права **только** этого замещения снимаются.
- После отзыва/окончания: незавершённая работа → ведущему менеджеру; **≠** автосмена ответственного в B24 (R4.4).

**История:**

- Действия ассистента **сохраняются** для уполномоченных (менеджер, РОП, audit).
- **Без другого действующего доступа** ассистенту **запрещены:** карточка, документы, задачи, вложения и **исторические записи, содержащие клиентские данные**.
- Собственные показатели эффективности ассистента — **отдельно** (**предложение**), без раскрытия недоступных клиентских данных.

### 4.6 Координатор (**требование** + **предложение**)

**Предложение (по умолчанию):**

- Просмотр **графика**, **загрузки**, **минимальных** сведений о замещениях (участники, сроки, статус).
- **Полный доступ к карточкам клиентов не выдаётся автоматически.**

**На согласование:**

- право **создавать / согласовывать / изменять / отзывать** замещения;
- границы «своих» команд координатора;
- отдельный grant на read карточек.

Координатор **не** становится замещающим менеджером без записи delegation.

### 4.7 Администратор

| **реализовано** | **целевая модель (предложение)** |
|-----------------|----------------------------------|
| admin-only read clients (4 GET) | технические операции: users, import, logs |
| | **не** принимает коммерческие решения по факту роли admin |
| | бизнес-назначения и исключения — **только** по решению уполномоченного руководителя **с аудитом** |
| | **убрать** неоднозначный «admin override» назначений без основания |

## 6. Серверная авторизация и срок замещения

### 6.1 Проверка на **каждом** серверном запросе (**требование**)

1. учётная запись **active** (не disabled/invited без политики);
2. есть **действующее основание** доступа (grant и/или delegation);
3. для delegation: статус **разрешает** доступ (см. §6.1.1);
4. для delegation: `starts_at` **наступило**;
5. для delegation: `ends_at` **ещё не наступило**;
6. delegation **не отозвано** (`revoked_at` пуст);
7. если для delegation **требуется согласование** — оно **получено** (`approved_by_user_id` и политика approval выполнены).

Сервер на **каждом** запросе самостоятельно проверяет допустимость delegation/grant, срок и отсутствие отзыва — **независимо** от фонового задания.

**Фоновое задание** может обновлять производные статусы (`expired`), уведомления и отчёты, но **не определяет** момент выдачи или прекращения доступа.

#### 6.1.1 Статусы delegation и согласование (**требование**)

| Статус | Доступ к клиентским данным |
|--------|----------------------------|
| `draft` | **нет** — даже если календарная дата уже внутри `[starts_at, ends_at)` |
| `pending_approval` | **нет** — даже после наступления `starts_at` |
| `active` | **да**, только если выполнены все условия §6.1 (включая approval, если требуется) |
| `revoked` | **нет** (с `revoked_at`) |
| `expired` | **нет** (производный; доступ уже закрыт по `ends_at` на запросе) |

**Правила:**

- Наступление даты **само по себе не является** согласованием и **не открывает** доступ.
- Если политика требует approval — доступ **запрещён** без записанного согласования уполномоченного лица.
- Перевод `pending_approval` → `active` — **отдельное** действие (или автоматика **только** если явно утверждена политика; по умолчанию — **на согласование** Q-APPR-1).

### 6.2 Границы срока (**предложение** — на согласование)

| Параметр | Предложение |
|----------|-------------|
| `starts_at` | **включительно** |
| `ends_at` | **исключительно** |
| Хранение | однозначные timestamptz (UTC в БД) |
| Отображение и ввод | **Europe/Moscow** |

> Подпись «(МСК)» в существующем UI карточки (**реализовано**) **не означает** согласования этой бизнес-политики сроков замещения.

### 6.3 Запись delegation (минимум полей)

`id`, `granted_by_user_id`, `assistant_user_id`, `scope` (fixed list или policy ref), `starts_at`, `ends_at`, `status`, `approved_by_user_id`, `revoked_by_user_id`, `revoked_at`, `revoke_reason`, `created_at`, `updated_at`, `change_history`.

### 6.4 Пересечения

| Ситуация | Правило |
|----------|---------|
| Два замещения одного ассистента | scope = union |
| Отзыв одного из двух | снимаются **только** права этого замещения; независимое основание **сохраняется** |
| Fixed-list delegation + новая ТТ под тем же клиентом | новая ТТ **не** в scope автоматически |

## 7. Безопасность

### 7.1 Endpoint coverage (**требование**)

list, detail, search, filters, options, sync-status, export, attachments — **server-side** scope filter.

### 7.2 Утечки через поиск, фильтры, счётчики, export и кэш (**требование**)

| Вектор | Требование |
|--------|------------|
| **Поиск (`q`)** | возвращает **только** объекты в разрешённом scope пользователя |
| **Фильтры** (manager, holding, phone, …) | применяются **поверх** scope; фильтр **не расширяет** доступ |
| **Справочники / reference data** (`/options`, списки менеджеров/холдингов) | **только** IDs и labels **разрешённых** объектов; без чужих подсказок |
| **`total` и pagination** | считают **только** доступные пользователю записи, не глобальный размер БД |
| **Export / bulk** | проверка прав **на сервере** перед формированием; export **не расширяет** scope и **не** обходит отзыв |
| **Кэш** (browser, reverse proxy, server) | **не смешивает** данные разных пользователей; **не обходит** отзыв grant/delegation или `disabled` |
| **Заголовки ответов** | для защищённых персональных/клиентских данных: `Cache-Control: private, no-store` (как минимум для API clients и export) |

### 7.3 Внешние системы

| Система | Правило |
|---------|---------|
| **1С** | read-only; права ЛК **не** разрешают запись |
| **B24** | доступ в ЛК **≠** права B24; смена ответственного — R4.4 (**отдельная** проверка) |
| **Рекламации** | только published summary (R2.4) |

### 7.4 Отзыв и обход

Старые сессии, кэш, export, прямые ссылки на вложения **не должны** обходить отзыв grant/delegation или `disabled`.
