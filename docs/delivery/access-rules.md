## 1. Что реализовано vs что требуется

### 1.1 Реализовано на `main`

| Компонент | Факт |
|-----------|------|
| Роли | 8 значений в `users.role` CHECK — `src/shared/user.ts` |
| Статусы | `invited`, `active`, `disabled` |
| Авторизация | сессия cookie, `requireAuth`, rate limit, CSRF Origin |
| Клиенты API | `GET /api/clients`, `/options`, `/sync-status`, `/:guid` — цепочка `requireAdmin` |
| Данные клиентов | таблица `onec_clients`: 8 полей + `guid_manager` из 1С; **нет FK** на `users` |
| UI | non-admin видит «Нет доступа» на `/clients`; сервер всё равно отвечает 403 |
| Интеграционные тесты | manager → 403 на clients API (`clients-workspace.test.ts`) |

### 1.2 Согласованные требования (v1.1 / прототип v2)

- Два менеджера **не видят** чужие записи (в т.ч. прямой API).
- РОП видит **свою** команду.
- Региональный — **только по назначениям**, не по городу.
- Замещение ассистентом — по датам, с возвратом работы (экраны 18–20 → R4).
- Права на **сервере** (экран 24).
- user ↔ стабильный ID сотрудника 1С — **не по ФИО/телефону/email**.

### 1.3 Предложения R1.3-prep (не реализованы)

- Таблицы: `user_onec_employee_links`, `access_grants`, `delegations`, `access_audit_log`.
- Policy engine: проверка на каждом endpoint и export.
- Разделение `admin` (ИТ) и `director` (бизнес-продажи).

| **1С: оргструктура** | РОП ↔ менеджеры, regional ↔ объекты | первичный для rop/regional | ❌ нет в 8 полях (R1.2 / Q8) |
| **ЛК: явное назначение** | marketer/analyst scope, assistant delegation | вторичный; auditable | 📋 R1.3 |
| **ЛК: роль пользователя** | потолок возможностей (director vs manager) | ограничитель | ✅ enum есть; enforcement ❌ |
| **Статус учётной записи** | `active` / `disabled` / `invited` | блокирующий | ✅ login + API |

### 2.1 Связь user ↔ сотрудник 1С (**требование**)

| Правило | Описание |
|---------|----------|
| PK связи | подтверждённый стабильный ID сотрудника 1С ↔ `users.id` |
| **Запрещено** | auto-link по `full_name`, `email`, `phone`, `name_manager` |
| Нет связи | доступ к клиентским данным **закрыт** (403 / пустой scope) |
| Конфликт (2 user на 1 employee, 2 employee на 1 user) | доступ **закрыт** до ручного разрешения admin |
| Увольнение / блокировка в 1С | триггер отзыва grants (**на согласование:** webhook vs периодический sync) |
| `disabled` в ЛК | немедленный отказ auth + инвалидация сессий |

## 3. Бизнес-правила по ролям

### 3.1 Менеджер (**требование**)

- Работает со **своей подтверждённой** базой: клиенты, где назначенный `employee_id` совпадает с привязкой user.
- **Не видит** чужих клиентов ни в списке, ни по прямому GUID, ни через поиск/фильтры/счётчики/export.
- Может **инициировать замещение** только по клиентам в своём scope (R4.3).

### 3.2 Региональный менеджер (**требование**)

- Видит клиентов и ТТ **только** по подтверждённым назначениям на объект.
- Одинаковый город, регион или территория **не дают** доступ сами по себе.
- Доступ к одной ТТ **не раскрывает** коммерцию/финансы всего холдинга.

### 3.3 РОП (**требование**)

- Видит **подтверждённую команду** и её клиентов.
- Может **корректировать доступы и замещения** в пределах команды.
- Не видит клиентов команд других РОП (если нет отдельного grant от director).

### 3.4 Директор по продажам (**предложение**)

- Область: **вся подтверждённая** клиентская база компании (sales scope).
- **Отдельно:** должность «директор по продажам» должна быть **подтверждена** как системная роль `director` — HR/владелец (**на согласование** процесс).
- **Не** технический `admin`: без управления миграциями, паролями других admin, raw import.

### 3.5 Ассистент (**требование**, реализация R4.3)

- Временный доступ к **выбранным** клиентам/объектам на период замещения.
- Видит **весь необходимый рабочий контекст** по ним (данные, задачи, заказы, отгрузки, документы, условия, финансы в scope).
- **Не** получает права admin/руководителя.
- Может замещать **нескольких** менеджеров одновременно (объединение scopes).
- По завершении/отзыве: доступ **прекращается**; незавершённая работа → ведущему менеджеру; **история действий сохраняется**.
- Замещение **≠** автоматическая смена ответственного в Битрикс24 (отдельная интеграция R4.4).

### 3.6 Координатор ассистентов (**требование** + **на согласование**)

- Планирование замещений и загрузки ассистентов.
- **Не предполагается** автоматически полный доступ ко всем клиентским данным.
- Точная область — см. [§8](#8-открытые-вопросы) Q-COORD-1.

### 3.7 Маркетолог, аналитик, категорийный менеджер (**предложение**)

- **Минимально необходимые** права под задачи роли (см. матрицу).
- **Не** вся клиентская база, **не** финансы, **не** управление доступом по умолчанию.

### 3.8 Администратор (**реализовано** как admin-only; **целевая модель**)

- **Техническое** администрирование: users, import runbook, диагностика.
- **Отделено** от бизнес-согласований коммерции и назначений менеджеров.
- Текущий режим «только admin видит клиентов» — **временный**, не модель для всех сотрудников.

## 4. Иерархия клиента и наследование

**Целевая структура (R1.2):** холдинг → юрлица и торговые точки; на каждом уровне — свои ответственные; **не** предполагать «одна ТТ = одно юрлицо».

### 4.1 Типы назначения

| Тип grant | Объект | Эффект (предложение) |
|-----------|--------|----------------------|
| `holding` | `guid_holding` | доступ к объектам холдинга согласно политике наследования |
| `legal_entity` | ID юрлица | юрлицо + связанные ТТ (**на согласование:** все связанные или whitelist) |
| `outlet` (ТТ) | ID ТТ | только ТТ + навигационный минимум родителя |
| `client_row` | `guid_client` | строка snapshot (текущий 8-field мир) |

### 4.2 Правила наследования (**предложение**)

1. **Назначение на холдинг** → доступ к дочерним юрлицам/ТТ, **если** нет более узкого deny.
2. **Назначение на юрлицо** → доступ к этому юрлицу и **явно связанным** ТТ; **не** автоматически все юрлица холдинга.
3. **Назначение на ТТ** → только ТТ; родитель — имя/ID для навигации **без** финансов холдинга.
4. **Доступ к родителю** при grant на дочернем уровне — **только** метаданные (имя, иерархия), не соседи.
5. **Несколько grants** → объединение (OR); конфликт deny vs grant — **на согласование** (рекомендация: explicit deny побеждает).
6. **Продажи** агрегируются по холдингу на уровне юрлиц → при доступе только к ТТ показывать **«недоступно / агрегат холдинга»**, не выдуманную долю ТТ.

### 4.3 Спорные правила (**на согласование**)

| ID | Вопрос |
|----|--------|
| Q-HIER-1 | Grant на юрлицо даёт доступ ко **всем** ТТ юрлица или только к перечисленным? |
| Q-HIER-2 | Менеджер на `guid_client` (строка snapshot) — наследует ли будущие юрлица/ТТ того же холдинга? |
| Q-HIER-3 | Regional на ТТ видит ли **адрес доставки**, не совпадающий с адресом ТТ? |

## 5. Безопасность и границы данных

### 5.1 Серверная проверка (**требование**)

- Каждый endpoint: list, detail, search, filters, options, sync-status, export, attachments (будущее).
- UI-сокрытие кнопок **не** считается контролем доступа.
- Ответ **403** или **404** (политика утечки ID — **на согласование**; рекомендация: 404 для чужого GUID).

### 5.2 Риски утечки (**требование** — учесть в R1.3)

| Вектор | Риск | Мера |
|--------|------|------|
| Справочники фильтров (`/options`) | IDs/имена чужих менеджеров/холдингов | фильтровать options по scope пользователя |
| `total`, pagination | count по всей БД | count только по разрешённому scope |
| Поиск `q` | match по чужим клиентам | SQL/WHERE с grant filter |
| Кэш (CDN, browser, server) | ответ admin закэширован для user | `Cache-Control: private, no-store` + Vary по auth |
| Export / bulk | выгрузка всей базы | отдельное право + audit |
| Агрегаты analyst | re-identification через малые группы | порог k-anonymity / suppression (**на согласование**) |

### 5.3 Внешние системы

| Система | Правило |
|---------|---------|
| **1С** | ЛК — read-only к snapshot; права ЛК **не** разрешают запись в 1С |
| **Битрикс24** | доступ в ЛК **≠** права в B24; смена ответственного в задачах — R4.4 |
| **Облако / фото** | отдельные ACL; ID ТТ обязателен (R3/R5) |
| **Рекламации (R2.4)** | только **опубликованная разрешённая сводка**; не вся задача, не внутренние комментарии |

## 6. Замещение и аудит

### 6.1 Минимальная запись замещения (delegation)

| Поле | Описание |
|------|----------|
| `id` | UUID записи |
| `granted_by_user_id` | кто передаёт (менеджер / РОП) |
| `assistant_user_id` | кто замещает |
| `scope` | список client/object IDs или ссылка на policy snapshot |
| `starts_at`, `ends_at` | границы (**Europe/Moscow**, inclusive start, exclusive end — **на согласование**) |
| `status` | `draft` / `pending_approval` / `active` / `revoked` / `expired` |
| `approved_by_user_id` | кто согласовал (если требуется) |
| `revoked_by_user_id`, `revoked_at`, `revoke_reason` | досрочный отзыв |
| `created_at`, `updated_at` | аудит |
| `change_history` | append-only JSON/array изменений |

### 6.2 Часовой пояс и границы срока

- Все даты замещения — **Europe/Moscow** (МСК), согласовано с UI «(МСК)» в карточке.
- **Предложение:** `starts_at` inclusive, `ends_at` exclusive; переход в `active` — по cron/worker ≤1 мин (**на согласование**).
- Досрочный отзыв: `revoked_at` effective immediately; assistant теряет доступ на следующем запросе.

### 6.3 Пересечения

| Ситуация | Предложение |
|----------|-------------|
| Два замещения одного ассистента | разрешено; scope = **union** клиентов |
| Два ассистента на одного менеджера | разрешено; scopes независимы |
| Пересечение сроков одного клиента у двух ассистентов | **на согласование** (split vs co-assist) |
| Менеджер вернулся досрочно | отзыв delegation; assistant сохраняет read-only историю своих действий |

### 6.4 Аудит доступа (access_audit_log)

- события: grant created/revoked, login denied (no link), export, forbidden API attempt.
- хранение: ≥ 1 год (**на согласование**).
- PII в логах: минимизация.

## 7. Выдача и отзыв (кто кому)

| Действие | Кто может | Кого/что |
|----------|-----------|----------|
| Привязка user ↔ 1C employee | admin | любой user |
| Назначение менеджера на клиента | 1С (primary) / director / admin override | client/object |
| Назначение regional | 1С / director | object |
| Состав команды РОП | 1С / director | managers |
| Замещение | manager (own clients), rop (team) | assistant user |
| Согласование замещения | rop / director (**на согласование**) | delegation |
| Маркeting/analyst scope | director / admin | campaign/report scope |
| Отзыв при увольнении | admin + sync 1С | all grants |

**Срок:** grant может быть бессрочным (менеджер) или временным (assistant); временные — обязательный `ends_at`.
