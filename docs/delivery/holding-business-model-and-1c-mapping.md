## 1. Целевая модель (бизнес)

### 1.1 Сущности (логические)

```text
Холдинг (группа)
  ├── Юридическое лицо (1..N)   — учётная сущность; в обмене сегодня не выделена отдельным GUID
  └── Торговая точка (0..N)     — нормализуется из retail_outlets[].guid_store
```

**У каждого клиента в смысле ЛК есть холдинг**, в том числе при одном юрлице и одной ТТ.

### 1.2 Четыре утверждённых типа состава (не ТОП / не «Категория 1С»)

| Тип | Юрлица (уник.) | ТТ (уник. guid_store) |
|-----|----------------|------------------------|
| **Холдинг моно** | 1 | 1 |
| **Холдинг моно сеть** | 1 | >1 |
| **Холдинг групп** | >1 | 1 |
| **Холдинг групп сеть** | >1 | >1 |

Классификация описывает **полный фактический состав холдинга** (когда он известен из данных), а не форму ссылки `guid_holding` и не фильтр списка.

### 1.3 Чему соответствует «запись клиента» в `all_clients.json`

| Логическая сущность | Типичное отображение в обмене сегодня | Не приравнивать |
|---------------------|----------------------------------------|-----------------|
| **Холдинг (корень группы)** | Отдельная строка с `holding=true` **или** (спорно) self-ref — см. §4–5 | `guid_client` ≠ «холдинг» без явной семантики |
| **Юридическое лицо** | **Не идентифицируется** отдельным подтверждённым ключом; реквизиты F3 лежат **на строке** | **`guid_client` ≠ юрлицо** до письменного «один guid_client = одно уникальное юрлицо» |
| **Торговая точка** | `retail_outlets[]` на строке; registry `onec_retail_outlets.guid_store` | Вложенность строки **не** доказывает эксклюзив «одно юрлицо — одна ТТ» |

### 1.4 Self-ref и тип состава

**Форма ссылки** (`guid_holding`, self-ref, `holding=true`) задаёт **идентичность и родительство** в snapshot, а **не** один из четырёх типов состава.

Самоссылочный «корень» (`guid_holding == guid_client`) **не** означает автоматически «Холдинг моно»: под таким корнем в 1С могут быть **несколько** юрлиц и **несколько** ТТ (дочерние строки, outlets на разных members).  
422 self-ref в SHA `a957ab33…` **нельзя** интерпретировать как 422 «моно» без отдельного анализа состава и контракта.

## 2. Сопоставление с текущим контрактом обмена

Легенда: **подтверждено** (код/тест/live audit) · **выводимо** (при явных правилах и полноте данных) · **не хватает** (нужен 1С/контракт).

| Поле / связь | Роль в целевой модели | Подтверждено | Выводимо однозначно | Не хватает |
|--------------|----------------------|--------------|---------------------|------------|
| `guid_client` | ID **строки** snapshot / PK `onec_clients` | PK, validate UUID | Membership по `guid_holding` / `holding` при полных связях | Ключ юрлица; «один row = одно юрлицо» |
| `guid_holding` | Ссылка на корень группы | Формат, tolerant/strict, cycle/self-ref rules | Parent chain при `holding=true` на цели | Семантика self-ref (422 в live) |
| `name_holding` | Имя группы на строке | Парность с `guid_holding` (HOLDING_CONTRACT) | — | Единое имя на всех members |
| `holding` (boolean) | Маркер **карточки-холдинга** | extended validate | Цель ссылки для потомков | — |
| `retail_outlets[].guid_store` | ID ТТ | extended, closure rules | Подсчёт **уник.** `guid_store` в membership **при известном membership** | Связь ТТ ↔ юрлицо(а) |
| F3-строки | Реквизиты на строке | F3 pipeline, типы (SHA `a957ab33…`) | **Не** реестр юрлиц | GUID юрлица, M:N юрлицо↔ТТ |

**Важно:** разные строки с разными `Контрагент` / `НаименованиеПолное` — только разные **строки snapshot**, не доказательство числа юрлиц.  
**До подтверждения 1С** соответствия «один `guid_client` = одно уникальное юрлицо» счётчик **`legalEntityCount` неизвестен**; тип состава **не вычисляется** по числу строк клиентов в membership.

## 3. Предложение: правила автоматической классификации (для приёмки)

### 3.1 Предпосылка для подсчёта юрлиц (блокер)

| Состояние | Поведение |
|-----------|-----------|
| Нет подтверждённого ключа юрлица **и** нет согласованного правила «1 guid_client = 1 юрлицо» | `legalEntityCount` = **unknown** → **`holdingCompositionType` = unknown** (тип **не** присваивается) |
| 1С подтвердило правило или выдало ключ (напр. `guid_legal_entity`) | Тогда §3.2–3.3 применимы |

Синтетические JSON в `proposed-contract/` **явно используют допущение предлагаемого контракта:** каждая member-строка (не `holding=true` shell) = **одно** иллюстрируемое юрлицо — **только для демонстрации четырёх типов**, не как текущий факт обмена.

### 3.2 Membership холдинга

1. **Корень:** по согласованному контракту (variant A/B) — **не** вывод «моно» из self-ref.
2. **Члены:** строки с transitive `guid_holding` на тот же корень (+ корень).
3. **Неполный membership** (`holdingLinkState=unresolved`, обрыв): тип **`unknown`** (не «моно»).

### 3.3 Подсчёт (только после §3.1)

| Счётчик | Правило (после подтверждения ключа юрлица) |
|---------|---------------------------------------------|
| **legalEntityCount** | Уникальные юрлица по **согласованному** ключу (или по правилу 1:1 с `guid_client`, если 1С подтвердит) |
| **outletCount** | Уникальные non-empty `guid_store` в membership |
| **Дедуп ТТ** | Один `guid_store` — один раз в outletCount |
| **0 юрлиц / 0 ТТ** | **Не** «моно» → `unknown` или отдельный бизнес-класс после O1–O2 |

### 3.4 Классификация (при известных legalEntityCount и outletCount)

```text
if legalEntityCount unknown OR outletCount unknown OR membership incomplete → unknown
else if legalEntityCount==1 && outletCount==1 → mono
else if legalEntityCount==1 && outletCount>1  → mono_network
else if legalEntityCount>1 && outletCount==1  → group
else if legalEntityCount>1 && outletCount>1  → group_network
```

### 3.5 Фактический тип vs доступность информации (R13)

Два **независимых** измерения:

| Измерение | Смысл |
|-----------|--------|
| **`holdingCompositionType`** | Фактический тип при **полном** составе холдинга в snapshot (§3.1–3.4). **Один и тот же** для всех ролей, если тип вообще вычислен. |
| **`compositionTypeVisibility`** (UI/API, черновик) | Может ли **текущий** пользователь **видеть** тип: `visible` / **`withheld`** («нет доступа к отображению состава») |

**Ограниченный scope менеджера не меняет** `holdingCompositionType` на `unknown`. Частичная видимость строк/ТТ — **не** «неизвестный состав», а **withheld** (или скрытие поля типа) без раскрытия точных счётчиков, скрытых `guid_client`, sibling outlets или реквизитов.

Тип холдинга **не расширяет** права доступа.

#### Тип состава × роль (черновик UI/API, R13)

Правила:

- При **полном** известном составе (§3.1–3.4) значение **`holdingCompositionType` одно и то же** для всех ролей.
- При **ограниченном scope** (видна только часть юрлиц/ТТ холдинга) тип **не** подменяется на `unknown`; если политика не показывает тип без полной видимости — **`withheld`** (без счётчиков и без sibling-реквизитов).
- При **неполных данных 1С** (нет ключа юрлица, обрыв membership, не вычислен `legalEntityCount` / `outletCount`) — **`unknown`** для всех ролей.

| Роль | `holdingCompositionType` (если вычислен) | Что видит пользователь (метка типа) |
|------|------------------------------------------|-------------------------------------|
| **manager** | Как у всех | **`visible`** — только если scope покрывает весь холдинг для отображения типа; иначе **`withheld`** |
| **regional_manager** | Как у всех | **`visible`** / **`withheld`** по тому же правилу (scope regional, без расширения через `guid_holding`) |
| **rop** | Как у всех | **`visible`** / **`withheld`** (scope команды РОП; не «unknown» из‑за частичной видимости) |
| **director** | Как у всех | **`visible`** при доступе к полному составу в snapshot; иначе **`withheld`** |
| **admin** | Как у всех | **`visible`** (тех. доступ к полному snapshot; без утечки PII вне политики аудита) |
| **Любая роль** | **Не вычислен** (`unknown`) | **`unknown`** — неполные данные 1С / membership, не scope |

## 4. Блокер обмена (SHA `a957ab33…`) и новая модель

### 4.1 Факты

2742 строки; F2–F5 OK; fail только holding-коды; **422×** self-ref без `holding`.

### 4.2 Бизнес-модель ≠ self-ref ≠ «моно»

«У каждого клиента есть холдинг» и четыре типа **не** подтверждают корректность 422 self-ref и **не** классифицируют их как «моно».

### 4.3 Вариант A — отдельная карточка холдинга (**предложение**)

| Аспект | Описание |
|--------|----------|
| **Идентичность** | Root-строка `holding=true`; members с `guid_holding → root` |
| **Validator ЛК сегодня** | Проходит first-read **без** self-ref |
| **Стоимость** | Изменения выгрузки 1С, сохранение GUID, согласование с реальными объектами 1С |
| **Не следует из этого** | Обязательная переделка 1С «потому что так удобнее validator» |

### 4.4 Вариант B — self-ref как корень (**предложение**)

| Аспект | Описание |
|--------|----------|
| **Идентичность** | `guid_holding = guid_client` = корень; **может** объединять много юрлиц/ТТ |
| **Validator ЛК сегодня** | Self-ref **блокируется** без нового контракта |
| **Реализация в ЛК** | **Отдельный PR** на parser/normalization (`detectHoldingCycles`, `holdingLinkState`, docs) — **не** Draft PR #71 (диагностика + модель). До merge такого PR **не** смешивать правки validator с документацией блокера. |
| **Стоимость** | Parser + docs + риски UI/доступа; **может** быть ближе к текущей форме 422 |
| **Не auto** | `holding=true`, очистка `guid_holding` |

Синтетика: `proposed-contract/holding-variant-b-self-ref-cluster.json` — **PROPOSED**, **не** проходит текущий first-read validator (см. README).

### 4.5 Выбор A/B

Решение **не** сводится к «что проходит validator». Учитывать: **реальная идентичность объектов 1С**, **сохранение GUID**, назначения ЛК, стоимость изменений **на стороне 1С и ЛК**. Multi-node cycles остаются ошибкой.

## 6. Вопросы к 1С / бизнесу

1. Ключ юрлица: отдельный GUID или подтверждение «1 `guid_client` = 1 юрлицо»?
2. Если **`guid_client` ≠ юрлицо**: как 1С будет передавать **`legalEntityCount`** или эквивалент (отдельное поле, массив GUID юрлиц, агрегат на корне холдинга, иное)?
3. **A или B** для идентичности корня (§4.5) — с учётом GUID и стоимости, не только validator; при **B** — отдельный PR на parser (§4.4), не смешивать с диагностикой #71.
4. Self-ref: семантика корня **без** автоматического «моно».
5. Передача связи **несколько юрлиц ↔ одна ТТ** (не продемонстрировано в `holding-group.json`).
6. O1–O4 (§3.6).

**Не запрашивать повторно:** F2–F5 на `a957ab33…`.
