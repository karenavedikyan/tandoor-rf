## 1. Целевая модель (бизнес)

### 1.1 Сущности (логические)

```text
Холдинг (группа)
  ├── Юридическое лицо (1..N)   — коммерческая/учётная «строка клиента» в обмене
  └── Торговая точка (0..N)     — нормализуется из retail_outlets[].guid_store
```

**У каждого клиента в смысле ЛК есть холдинг**, в том числе при одном юрлице и одной ТТ.

### 1.2 Четыре утверждённых типа состава (не ТОП / не «Категория 1С»)

| Тип | Юрлица (уник.) | ТТ (уник. guid_store) |
|-----|----------------|------------------------|
| **Холдинг моно** | 1 | 1 |
| **Холдинг моно сеть** | 1 | >1 |
| **Холдинг групп** | >1 | 1 |
| **Холдинг групп сеть** | >1 | >1 |

Классификация описывает **полный состав холдинга в snapshot**, а не фильтр списка и не видимую пользователю подмножество.

### 1.3 Чему соответствует «запись клиента» в `all_clients.json`

| Логическая сущность | Типичное отображение в обмене сегодня | Не приравнивать |
|---------------------|----------------------------------------|-----------------|
| **Холдинг (корень группы)** | Отдельная строка с `holding=true` **или** (спорно) та же строка, что юрлицо — см. §5 | `guid_client` ≠ «холдинг» без явной семантики |
| **Юридическое лицо** | Строка массива с `guid_client`; реквизиты F3 на **этой строке** | `name_client` / `Контрагент` ≠ отдельный GUID юрлица |
| **Торговая точка** | `retail_outlets[]` на строке; registry `onec_retail_outlets.guid_store` | Одна ТТ может фигурировать в JSON на одной строке; связь «несколько юрлиц → одна ТТ» **не подтверждена** жёсткой вложенностью |

## 2. Сопоставление с текущим контрактом обмена

Легенда: **подтверждено** (код/тест/live audit) · **выводимо** (при полном snapshot и правилах §3) · **не хватает** (нужен 1С/контракт).

| Поле / связь | Роль в целевой модели | Подтверждено | Выводимо однозначно | Не хватает |
|--------------|----------------------|--------------|---------------------|------------|
| `guid_client` | ID **строки** snapshot / PK `onec_clients` | PK, validate UUID | Принадлежность строки к холдингу **не** без `guid_holding` / `holding` | Отдельный GUID «юрлица» vs «клиента UI» |
| `guid_holding` | Ссылка на корень группы (UUID **другой строки** или пусто) | Формат, tolerant/strict, cycle/self-ref rules | Цепочка parent при `holding=true` на цели | Явная семантика self-ref (422 в live) |
| `name_holding` | Отображаемое имя группы на строке | Парность с `guid_holding` (HOLDING_CONTRACT) | — | Единое имя на всех членах группы (не enforced) |
| `holding` (boolean) | Маркер **карточки-холдинга** (`isHolding`) | extended validate | `holding=true` → цель ссылки `guid_holding` | Связь «моно = один row без holding card» |
| `retail_outlets[].guid_store` | ID ТТ | extended, closure, uniqueness rules | Подсчёт уник. ТТ **внутри snapshot файла** | Привязка ТТ к **конкретному** юрлицу при shared ТТ |
| F3: `Контрагент`, `НаименованиеПолное`, `ЮрФизЛицо`, `Оптовик_ОГРН` | Реквизиты **на строке** | F3 pipeline, типы string/null (SHA `a957ab33…`) | **Не** справочник уник. юрлиц; **не** доказательство числа юрлиц в группе | GUID юрлица, связи M:N юрлицо↔ТТ |
| F2 / F5 на строке | Клиентские commercial/code поля | Подтверждены F2–F5 | — | Не путать с типом холдинга |

**Важно:** разные строки с разными `Контрагент` / `НаименованиеПолное` **не** автоматически означают разные юрлица в смысле учёта — только разные **строки snapshot**. Число юрлиц для типа холдинга предлагается считать по **уникальным `guid_client` в membership одного холдинга** (§3), пока 1С не даст иной ключ.

## 3. Предложение: правила автоматической классификации типа (для приёмки)

**Область:** вычисление `holdingCompositionType` для **полного** холдинга по данным snapshot (после успешного import), с учётом **scope** при отображении (§3.4).

### 3.1 Membership холдинга

1. **Корень:** строка с `holding=true` и пустым/корректным `guid_holding`, либо согласованный корень по **будущему** контракту (§5) — **не** автоматически `guid_holding = guid_client`.
2. **Члены:** все строки, у которых `guid_holding` (transitive closure) указывает на тот же корень; плюс корневая строка.
3. **Неизвестный/обрыв ссылки:** `holdingLinkState=unresolved` — membership **неполный** → тип **`unknown`**, не «моно».

### 3.2 Подсчёт юрлиц и ТТ

| Счётчик | Правило |
|---------|---------|
| **legalEntityCount** | Число **различных** `guid_client` в membership, **кроме** строк только с `holding=true` без собственных реквизитов юрлица — **открытый вопрос** (§6); черновик: все строки-members кроме чистого holding-shell |
| **outletCount** | Число **различных** `guid_store` (non-empty UUID) по всем членам membership |
| **Дедупликация ТТ** | Один `guid_store` считается **один раз**, даже если JSON дублирует ТТ на нескольких строках |
| **Shared ТТ** | Несколько юрлиц, одна ТТ — **допустимо** в модели; **не** умножать outletCount |

### 3.3 Классификация

```text
if membership incomplete OR legalEntityCount==0 OR outletCount unknown → unknown
else if legalEntityCount==1 && outletCount==1 → mono
else if legalEntityCount==1 && outletCount>1  → mono_network
else if legalEntityCount>1 && outletCount==1  → group
else if legalEntityCount>1 && outletCount>1  → group_network
```

**Запрет:** при `outletCount==0` **не** присваивать «моно» (→ `unknown` или отдельный бизнес-тип после решения §6).

### 3.4 Scope и доступ (R13)

- Тип холдинга **не расширяет** права: manager видит только назначенные ТТ/клиентов; **не** показывать точные счётчики полного состава, если часть скрыта — максимум «частично видим» / `unknown` для UI.
- Классификация для **фильтра списка** по полному snapshot (admin/director) vs **карточки** (scope-reduced) — **два режима**; фильтр **не** должен использовать только видимые строки как полный состав.

### 3.5 Открытые решения (бизнес ещё не принимал)

| # | Вопрос |
|---|--------|
| O1 | Учитывать ли **закрытые** ТТ (`closed=true`) в outletCount? |
| O2 | Поведение при **0 ТТ** или **0 юрлиц** в membership |
| O3 | Критерий **полноты** membership (все ли строки файла для `guid_holding` root) |
| O4 | **Когда** пересчитывать тип (каждый import / lazy / versioned) |

## 4. Блокер обмена (SHA `a957ab33…`) и новая модель

### 4.1 Факты (read-only Computer, без изменений)

- 2742 строки, 2145 nested outlet rows; F2–F5 OK; fail только holding-коды; **422×** `guid_holding == guid_client`, `holding` absent.

### 4.2 Бизнес-модель ≠ подтверждение self-ref

Утверждение «у каждого клиента есть холдинг» **не** доказывает, что **422 самоссылки** — корректный корень. Это отдельное решение контракта 1С (§5).

### 4.3 Вариант A — отдельная карточка холдинга (рекомендуется)

| Аспект | Описание |
|--------|----------|
| **Идентичность** | `guid_client` холдинга = root; юрлица — дочерние строки с `guid_holding → root` |
| **Связи** | Совместимо с `holding=true`, `validateHoldingTargets`, без self-ref |
| **Старый обмен** | Требует **нормализации** 422 self-ref → root card + children (источник) |
| **UI** | Корень может не иметь ТТ; юрлица и ТТ на дочерних строках |
| **Доступ** | Без изменений R13: ссылка `guid_holding` **не** расширяет sibling scope |
| **Validator** | Настоящие циклы A→B→C→A остаются **ошибкой** |

### 4.4 Вариант B — строка клиента = корень холдинга (self-ref)

| Аспект | Описание |
|--------|----------|
| **Идентичность** | Одна строка: `guid_holding = guid_client`, семантика «я корень» |
| **Связи** | Потребует **нового** контракта и изменения `detectHoldingCycles` (отдельный PR) |
| **Старый обмен** | Ближе к текущему **422**, но **конфликтует** с docs «самоссылки всегда ошибка» |
| **UI** | Меньше строк; риск смешения юрлица и холдинга в одной карточке |
| **Доступ** | Риск неправильной интерпретации sibling; нужны явные правила |
| **Validator** | Self-ref разрешить **только** при явном flag/контракте; **не** auto `holding=true` |

**Рекомендация:** **вариант A** — согласован с текущим validator и [clients-field-contract.md](./clients-field-contract.md); 422 трактовать как **несогласованность выгрузки с контрактом ЛК**, а не как автоматически верную «моно» модель.
