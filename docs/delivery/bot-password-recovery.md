# Восстановление пароля через MAX и Telegram

Реализация для существующего ЛК в PR #146. Merge и деплой не разрешены и не выполняются;
рабочая миграция, настройка сервера и реальные сообщения требуют отдельного согласования.

## Сотрудник запрашивает код администратору

- **Где:** на странице входа открыть «Забыли пароль?».
- **Действия сотрудника:** ввести свой логин, выбрать MAX или Telegram и нажать
  «Восстановить пароль через бота». Вход и привязка собственного бота не требуются.
- **Получатель:** единственный администратор, заданный серверной настройкой
  `PASSWORD_RECOVERY_ADMIN_USER_ID`. Код направляется только в его существующий
  подтверждённый бот выбранного канала. Публичная форма не задаёт администратора или chat ID.
- **Сообщение:** ФИО и логин восстанавливаемого аккаунта, код, срок действия и явное
  предупреждение о неавторизованном запросе. ФИО не доказывает личность отправителя.
- **Действия администратора:** лично проверить, что обратился именно указанный сотрудник,
  и только затем передать ему код. Без подтверждения запрос следует проигнорировать.
- **Действия сотрудника после передачи:** войти с логином и кодом, установить постоянный пароль.
- **До входа:** текущий пароль и сессии сотрудника не изменяются.
  Публичный ответ одинаков независимо от наличия аккаунта, конфигурации и доступности бота.
- **Без получателя:** отсутствующая/некорректная настройка, неактивный получатель, роль
  не администратора, требование сменить его пароль или недоступный бот блокируют доставку.
  Автовыбора первого администратора и переключения в собственный бот сотрудника нет.

## Сценарий администратора

- **Где:** «Настройка доступа», блок «Восстановление пароля сотруднику».
- **Действия:** точный логин сотрудника, собственный текущий пароль администратора,
  основание, выбор MAX/Telegram и подтверждение.
- **Получатель:** только существующая подтверждённая привязка бота авторизованного администратора.
  Передать произвольный номер, chat ID или другого получателя через API нельзя.
- **Результат:** администратор получает код и лично передаёт сотруднику.
  Пароль и сессии сотрудника остаются действующими до успешного входа по коду.
- **Ограничение:** этот сценарий не сбрасывает пароли других администраторов.
  Для своего административного аккаунта используется собственный бот через страницу входа.

## Подпись сообщения

Пример шаблона, не действующие данные:

```text
Тандор. Восстановление доступа.
Для кого: ФИО сотрудника
Логин сотрудника: employee@example.test
Запросил администратор: ФИО администратора (admin@example.test).
Временный код: [8 цифр]
Действует 10 минут, только для одного входа с обязательной сменой пароля.
Вы запросили код как администратор. Передайте его только указанному сотруднику лично.
```

При запросе без входа сообщение вместо имени инициатора содержит:
«Запрос: со страницы входа без авторизации. Личность инициатора ещё не подтверждена».
ФИО и логин восстанавливаемого аккаунта остаются в сообщении. Нельзя объявлять владельца
введённого логина достоверным инициатором неавторизованного запроса.

## Собственный доступ и вход по коду

- **Собственный доступ администратора:** на странице входа открыть «Забыли пароль?»,
  указать свой логин и канал. Код приходит только в собственный заранее привязанный бот
  этого администратора; настройка получателя запросов сотрудников для этого не нужна.
  Код административного аккаунта никогда не отправляется другому администратору.
- **Доступ сотрудника:** код по его публичному запросу получает назначенный администратор,
  как описано выше. Сотруднику не нужен собственный бот.
- **Привязка:** при остановленном боте или отключённых уведомлениях новый канал не создаётся.
- **Вход:** отметить «Войти по временному коду из бота», ввести логин и код.
  После входа обязательно выбрать постоянный пароль, введя тот же код в поле
  «Текущий пароль или временный код из бота».
- **Ограниченная сессия:** разрешены чтение собственного профиля/сессии, смена пароля и выход.
  Изменение профиля, бизнес-API и работа с бот-привязками до смены запрещены.
  Сессия смены действует 10 минут после входа; после смены используется обычный срок сессии.
- **Без бота у назначенного получателя:** сотруднику помогает действующий администратор через свой бот.
  Администратору без доступного привязанного бота требуется ручная помощь владельца.

## Защита

- **Код:** 8 случайных цифр, срок 10 минут, максимум 5 попыток, один вход.
  Повторный запрос доступен через 60 секунд и отменяет прежний неиспользованный код.
- **База:** HMAC-SHA-256 с существующим `TT_OTP_PEPPER` и отдельным пространством
  `password-recovery`. В БД, HTTP-ответах, аудитах и outbox нет открытого кода.
- **Привязка:** код закреплён за аккаунтом, выбранным каналом, получателем и снимком
  подтверждённой бот-привязки. Перепривязка, остановка бота, смена пароля/статуса
  делают его непригодным. Отзыв/удаление инициирующей административной сессии отменяет
  код, выданный авторизованным администратором.
  Публичный запрос сотрудника не требует административной сессии, но проверяет
  неизменность назначенного получателя при входе по коду.
- **После подтверждения:** старый пароль заменяется неизвестным случайным, старые сессии отзываются.
  Код не становится обычным паролем и не допускает повторный вход даже до выбора постоянного пароля.
- **Транзакции:** запрос, проверка, отзыв сессий и аудит защищены блокировками;
  параллельное предъявление одного кода создаёт ровно одну сессию.
  Ошибка доставки не изменяет действующий пароль, ошибка аудита откатывает локальные изменения.
- **Атрибуция:** запрос авторизованного администратора записывается от него;
  вход по коду записывается от восстанавливаемого аккаунта с отдельным ID выдавшего код администратора.
  Анонимный запрос хранится в challenge, не приписывается авторизованному пользователю в access audit.
  Для него при входе фиксируются получатель-администратор и происхождение `login_page`,
  но не утверждается, что администратор сам инициировал запрос.
  Явный `request_kind` не позволяет после удаления административной сессии ошибочно
  превратить её запрос в публичный запрос сотрудника.
- **Перебор и CSRF:** используются существующие механизмы с отдельными recovery-buckets.
  Ограничение восстановления не блокирует обычный парольный вход.

## Интеграция и выпуск

- **Повторное использование:** существующие таблицы привязок и ограниченные по времени
  транспорты MAX/Telegram; учитываются действующие флаги integration/delivery и уведомлений.
  Никаких новых токенов, внешних получателей, расписаний или воркеров.
- **Миграция:** `081_bot_password_recovery.sql`, только новая таблица, индексы и nullable-ссылка в sessions.
  Не меняет роли, телефоны, клиентов, передачи и существующие привязки.
- **Настройка получателя при согласованном выпуске:** установить серверную переменную
  `PASSWORD_RECOVERY_ADMIN_USER_ID` в UUID выбранного владельцем действующего администратора.
  Сверить UUID с его аккаунтом и проверить существующую привязку нужного канала.
  Это не секрет и не новый токен, но изменение рабочей конфигурации требует отдельного разрешения.
  В этом патче рабочая конфигурация не изменяется. UUID не берётся из HTTP-запроса и не публикуется в HTML.
- **Тесты:** `test/integration/bot-password-recovery.test.ts`,
  `test/browser/bot-password-recovery.browser.test.ts`,
  `test/unit/bot-password-recovery-delivery.test.ts`.
  Только синтетическая тестовая БД и подменённые транспорты.
- **Приёмка после согласованного выпуска:** отдельный разрешённый сценарий с реальным ботом администратора.
  Не запускать импорт 1С или планировщики для проверки восстановления.
- **Откат:** новую таблицу/колонку можно оставить для совместимости. Перед возвратом старого приложения
  необходимо с отдельным разрешением отозвать новые сессии, у которых
  `password_recovery_challenge_id IS NOT NULL`, и отменить pending challenges.
  Иначе старая версия не умеет завершить новую процедуру смены пароля по коду.

Сетевой таймаут после принятия сообщения ботом либо сбой подтверждения COMMIT может привести
к получению неработающего кода. Интерфейс не повторяет запрос автоматически: пользователь проверяет
бот и осознанно запрашивает новый код. Успешной реальной доставкой локальные тесты не являются.

## Результаты локальной проверки

Проверено 10.11.2026 на Node.js 22 и отдельной синтетической PostgreSQL-БД.
Реальные пользователи, сообщения в MAX/Telegram и рабочая БД в этих проверках не использовались.

- **Новая функция с публичным запросом сотрудника:** 30/30 проверок:
  22 интеграционных, 5 браузерных, 3 транспорта.
  Для MAX и Telegram отдельно проверены доставка публичного запроса назначенному администратору,
  отсутствие необходимости в боте сотрудника и отсутствие ложной атрибуции администратору.
- **Общий модульный набор:** актуальный `npm test`, 1440/1440 успешно
  (без `TEST_DATABASE_URL`; предыдущий запуск с этой переменной на `aa1682b` включал 1442 теста).
- **Сборка:** `npm run typecheck`, `npm run build`, `git diff --check` успешно.
- **Браузер:** фактические формы администратора и восстановления собственного доступа,
  вход по коду, обязательная смена пароля, обычный вход по временному паролю и ширина 375px.
- **Предыдущий расширенный интеграционный прогон на `aa1682b`:** 121 тест,
  94 успешно, 27 неуспешно. Полностью зелёным этот прогон не является;
  результат не переносится на последующее изменение как новый полный прогон.
- **Сравнение с исходной версией:** на отдельном checkout `c4b791e` и отдельной тестовой БД
  воспроизведены те же 25 неуспешных сценариев `access-control` (вместо ожидаемого назначения
  возвращается запрет до загрузки новой базы 1С), устаревшее ожидание списка миграций
  в `auth-profile` (заканчивается на `033`) и ошибка файла `admin-provisioning` из-за
  асинхронных событий завершения соединений после сброса тестовой БД.
  Эти исходные проблемы не исправлялись в патче восстановления.

Все проверки выполняются на синтетических данных; они не подтверждают реальную доставку.
Merge, настройка получателя, миграция рабочей БД, деплой и приёмка реальной доставки
остаются отдельно согласуемыми действиями.
