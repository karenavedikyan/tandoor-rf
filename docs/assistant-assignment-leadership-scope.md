# Назначения: резервирование РОА руководителями

Решение владельца от 05.11.2026: распределение остаётся основной задачей РОА, но его отсутствие не останавливает работу. Директор может выполнить полный операционный цикл по всей компании, РОП только по своей текущей команде.

## Границы реализации

- РОА сохраняет существующую область всех территорий.
- Директор и РОП получают создание, исправление, отправку, отмену неподтверждённой заявки, согласование, отклонение, возврат, предложение/решение изменений и отзыв доступа.
- Создание само по себе не выдаёт доступ: требуется отдельное согласование. Новый запрет самостоятельного согласования не вводится, существующий двухшаговый процесс сохраняется.
- Команда РОП проверяется на сервере по действующим связям и подтверждённой структуре 1С, как в клиентском реестре. Отсутствующая, отозванная или неоднозначная связь сотрудника не даёт доступа. Дополнительная видимость клиента сама по себе не делает чужого менеджера членом команды.
- Одна проверка области используется для менеджеров, списка/карточки, операций, подбора клиентов, журнала и уведомлений. После выхода менеджера из команды старое уведомление не раскрывает назначение.
- При выборе и согласовании клиентов действуют текущая принадлежность передающему менеджеру, текущая видимость руководителя и явные запреты. Пересечения назначений, сроки и версии не обходятся.
- Сохраняются реальный инициатор, передающий менеджер, роль и основания каждого действия. При работе за менеджера авторство не подменяется.
- Обязательную оценку оставляет только сам передающий менеджер. РОП не получает сводку оценок или приватные уведомления об оценках.
- Директор не становится техническим администратором: схемы, назначение ролей, пароли, импорт и интеграции не расширяются. Административный предпросмотр остаётся read-only.

## Проверки

`test/integration/assignment-leadership-scope.test.ts` проверяет полный цикл директора/РОП, чужие UUID, подделку менеджера/клиентов, изменение команды, подтверждённую структуру 1С без ручной связи, потерю связи сотрудника, явные запреты, CSRF, приватность оценок, технические операции и read-only предпросмотр.

`test/browser/assignment-leadership.test.ts` использует только локальную синтетическую базу. Проверяются создание, согласование, изменение и отзыв директором и РОП через настоящий интерфейс, ограниченный список менеджеров, журнал, read-only ассистент, desktop/mobile 375px и ошибки JavaScript.

Дополнительно запускаются существующие назначения, оценки и область клиентского реестра, общие unit-проверки, typecheck и сборка. Результаты конкретного запуска фиксируются в сдаче; старые результаты не переносятся на изменённый код.

Локальная проверка 05.11.2026: четыре интеграционных набора 42/42, браузерный набор 3/3, typecheck, build, синтаксис JS и `git diff --check` прошли. Общий unit-запуск выполнил 1434 проверки; DB-зависимый набор из двух проверок не инициализировался без `TEST_DATABASE_URL` и затем отдельно прошёл 2/2 с явной локальной тестовой базой. Итого 1436 unit-проверок выполнены в двух запусках, а не единым полностью настроенным прогоном.

В среде проверки Playwright запускался с `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`, указывающим на установленный Chromium; по умолчанию требуется установленный браузер соответствующей версии Playwright. Production-база и реальные назначения в проверках не использовались.

## Выпуск

Изменения подготовлены в отдельной локальной ветке от действующей production-ветки. Публикация, merge и Timeweb deploy в рамках этой подготовки не выполняются без отдельного разрешения владельца.

Новых миграций, изменений рабочих ролей или данных, импорта 1С, внешних уведомлений и запуска worker нет. После согласованного выпуска требуется проверить здоровье приложения и реальный пилот директора/РОП с подтверждённым составом команды, без произвольного изменения клиентских назначений.
