# Обязательные оценки ассистентов и уведомления

Подготовка к переносу из прототипа в рабочий ЛК. Этот документ не подтверждает выпуск: production-деплой и миграция 051 требуют отдельного согласования владельца.

## Поведение

- **Передающий менеджер:** после завершения согласованного периода видит постоянное напоминание и вкладку «Оценить работу». Для закрытия нужны 1–5 звёзд и комментарий от 10 до 2000 символов. Чтение уведомлений, Escape и возврат к списку не отменяют обязанность.
- **РОА и директор:** видят завершённые периоды, среднюю оценку, количество отзывов, оценки 1–3 в зоне внимания и незакрытые периоды. Есть поиск, фильтры по ассистенту, менеджеру, оценке и наличию оценки. Сводка рассчитывается по всей разрешённой истории, независимо от фильтра списка.
- **Приватность:** автор видит свои отзывы, РОА и директор все. Ассистент, РОП, другой менеджер и технический администратор не получают отзыв через API или интерфейс. Клиентский снимок дополнительно ограничен текущими правами и явными запретами. В общем техническом аудите записывается только факт отправки, без оценки и комментария.
- **Доступ:** срок доступа не зависит от отзыва. Черновики, несогласованные, будущие, активные и отменённые до старта назначения оценить нельзя. Досрочный отзыв оценивается только если согласованная работа действительно началась. Пока согласовывается изменение условий, оценка недоступна.
- **Неизменяемость:** один отзыв на назначение, повторная отправка не перезаписывает его. Сохраняются согласованные условия, фактические даты работы и клиентский снимок. Редактирование, удаление или оценка за другого сотрудника не предусмотрены.
- **Исключения по автору:** оценка относится к аккаунту передающего менеджера, а не к создателю заявки РОА. Автоматической передачи этой обязанности после смены роли, увольнения или для исторического назначения на передающего РОП нет. Такие случаи требуют отдельного решения владельца, без расширения прав других руководителей.

## Уведомления

Используется один общий колокольчик существующей оболочки, а не отдельный центр для оценок. Он работает на клиентах, продажах и назначениях для поддерживаемых ролей.

- **Менеджер:** решения по заявке, завершение периода, обязательная оценка и подтверждение отправки. Напоминание об оценке независимо от прочитанных сообщений.
- **Ассистент:** состояние временного доступа, начало и завершение периода, изменения. Нет баллов и комментариев. Переход из согласованного назначения открывает разрешённую клиентскую базу.
- **РОА:** заявки, изменения и события назначений, новые отзывы. Оценки 1–3 выделены сообщением о зоне внимания.
- **Директор:** действия РОА и новые отзывы с переходом к просмотру, без возможности оценивать за менеджера.
- **РОП:** прежние разрешённые события назначений; отзывы и уведомления о них не добавляются.

Есть общий счётчик непрочитанных, фильтр «Все / Непрочитанные», чтение одного или всех сообщений, страницы по 30 и собственная прокрутка ленты. Даты показаны в МСК. Обновление идёт при открытии ленты, возвращении на страницу и раз в минуту; временные границы учитываются по серверному времени. Изменение `scopeRevision` обновляет реестр ассистента после досрочного отзыва доступа.

Внешняя отправка в Б24, MAX, Telegram, email и другие каналы не подключается.

## Проверки перед выпуском

Проверки выполняются только на отдельных локальных БД с синтетическими сотрудниками и клиентами. Тестовые помощники запрещают использовать URL базы без суффикса `_test`.

- **Сборка:** `npm run build`, синтаксис обоих новых/обновлённых frontend-модулей, `git diff --check`.
- **Unit:** полный `npm test`.
- **Integration:** `node --import tsx --test --test-concurrency=1 test/unit/assignment-reviews.test.ts test/integration/assistant-assignments.test.ts test/integration/assignment-reviews.test.ts` при заданном `TEST_DATABASE_URL` отдельной тестовой БД. Проверяются конкурентные отправки, фильтры и страницы, CSRF, чужие аккаунты, завершение доступа, смена роли, запреты на клиентов и приватность.
- **Браузер:** `scripts/qa-assistant-reviews.mjs` экспортирует `runAssistantReviewQA({browser,origin,shotsDir})`. Нужен запущенный локальный сервер и предварительный `seedReviewQa` из `test/helpers/assistant-review-fixtures.ts` в другой тестовой БД. Проверяются реальное сохранение и reload, ошибки и повторная попытка, клавиатура, мобильный экран, обе темы, уведомления, полноэкранные списки и отзыв доступа РОА. Нельзя направлять этот сценарий в production.
- **Данные для визуальной проверки:** 9 назначений, два менеджера и два ассистента, 10–12 юрлиц в основных завершённых периодах, несколько полученных оценок и незакрытых периодов. Это не реальные сотрудники и не импорт в рабочую базу.

## Порядок согласованного выпуска

### До изменений

- Зафиксировать согласование PR и миграции 051. Проверить, что production работает на согласованном исходном коммите и уже применена 050.
- Сделать резервную копию БД и записать её идентификатор, прежний commit SHA и текущую версию схемы.
- Снять количества пользователей, связей с 1С, юрлиц, ТТ, назначений, запросов изменений, истории и уведомлений. Новый счётчик оценок до 051 равен нулю.
- Проверить исключения по автору: если уже есть назначения с передающим РОП или неактивным/сменившим роль менеджером, сначала согласовать обработку этих случаев. Не заменять автора автоматически.

### Выпуск кода и схемы

- Объединить согласованный PR и запустить деплой точного merge SHA. Само создание PR не выпускает код.
- После доступности кода технический администратор выполняет `POST /api/access/assignments/reviews/schema` с `{"confirm":true}`, действующей сессией и корректным Origin/CSRF.
- Endpoint принимает только фиксированную миграцию `051_assistant_assignment_reviews.sql`, требует admin, транзакционную advisory-блокировку, ожидаемую базовую схему и отсутствие других неприменённых миграций. Переданные пользователем SQL или имена файлов не выполняются.
- 051 только добавляет таблицу `assistant_assignment_reviews` и два индекса. Она не меняет пользователей, роли, пароли, связи 1С, продажи, клиентов, назначения или существующую историю.
- Сравнить `before` / `after` из ответа. При отличии количества записей транзакция отменяется. Если из-за параллельной работы пользователей счётчики изменились, сначала проверить причину, а не обходить защиту.
- Проверить, что 051 появилась в `schema_migrations`, затем выполнить `/api/health`, `/api/ready` и smoke-проверки прав под согласованными аккаунтами.

До подготовки 051 существующие назначения и уведомления остаются доступны, а API оценок отвечает контролируемым 503. Отрицательный результат проверки наличия таблицы не кэшируется, поэтому после применения схемы отдельный перезапуск для включения оценок не нужен.

### После выпуска

- Проверить один колокольчик на клиентах, продажах и назначениях; темы и мобильный экран. Проверить переход к уже существующей записи без создания вымышленных рабочих назначений или отзывов.
- При отсутствии завершённых периодов показывается пустое состояние, а не демонстрационные данные.
- Сохранить SHA, результат деплоя, версию схемы и счётчики. Не перевыпускать пароли, не загружать 1С повторно и не подключать внешние каналы в рамках этого выпуска.

## Откат

При необходимости вернуть прежний код. Аддитивную таблицу и сохранённые оценки не удалять, не сбрасывать схему и не восстанавливать весь backup поверх текущих данных без отдельного решения. Предыдущий код продолжает работать с прежними назначениями; сроки и ограничения доступа не зависят от наличия отзывов.
